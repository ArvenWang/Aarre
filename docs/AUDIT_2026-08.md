## 0. 一句话结论

这个项目的**功能覆盖度已经很高**，问题不在"缺功能"，而在**几个地基没打对，导致上层反复出问题、反复打补丁**。

具体说，我找到 **4 个真正的根因**。它们解释了你遇到的绝大多数症状，而且此前几轮修复都**没有命中**其中任何一个：

| # | 根因 | 它导致了什么 |
|---|---|---|
| **R1** | 书签的云端 ID 是用 **Chrome 本地书签 ID** 算出来的 | 两台电脑对同一个书签算出**两个不同的云端 ID**，于是每次同步都在**互删对方的记录**。你的双机同步一直在打架。 |
| **R2** | 图片资产的 ID 里**混进了内容哈希** | 换封面 = 内容变了 = ID 变了，但服务端认为"这个位置已经绑定了别的内容"→ 报 409，同步卡死。 |
| **R3** | 修 409 的那段"防御代码"**本身有 bug** | 换新 ID 上传，却拿**旧 ID** 去确认。服务端校验一个对不上的对象 → 报 422。这就是最近三天一直在修但修不好的 422。 |
| **R4** | 定时同步**只上传图片、从不下载图片** | 另一台机器换的封面，这台机器永远等不到，除非你重启浏览器或手动点同步。 |

前三个都是**几行代码级别的确定性错误**，不是玄学。第四个是漏了一行调用。

除此之外，还有一批"设计层面欠账"（Agent 架构过时、首屏 773KB、UI 双轨样式），这些不是 bug，是需要重做的部分。

## 1. 云端同步系统

### 1.1 先说结论：你的判断基本正确，但根因猜错了方向

你说"应该是里面的一些问题，比如标签的 ID 不唯一之类的，或者有一些脏数据"。

**方向对了，但具体对象不是标签。** 标签（tags）在系统里就是一个字符串数组，没有独立 ID，服务端合并时用 `Set` 去重，这块反而是健康的。

真正 ID 不唯一的是**「收藏位置」（bookmark-item）**和**「图片资产」（asset）**。而且不是"偶尔不唯一"，是**结构性必然不唯一**。

### 1.2 R1：两台电脑在互删对方的记录（最严重）

#### 现在的代码

```343:348:src/lib/cloud-state.ts
    // 收藏位置 ID 由 Chrome 书签 ID 确定性派生：同一书签在重装、
    // 换扩展 ID 后仍保持同一 ID，云端按 ID upsert 而不是新增。
    const payload: BookmarkItemPayload = {
      bookmarkItemId:
        existing?.bookmarkItemId ||
        (await stableUuid(`bookmark:${hint.id}`)),
```

这里的 `hint.id` 是 **Chrome 分配的本地书签 ID**（就是 `"153"`、`"287"` 这种数字字符串）。

#### 为什么这是错的

Chrome Sync 会把书签的**内容**（标题、网址、文件夹）同步到你的另一台电脑，但**不会同步本地 ID**。每台机器的 Chrome 独立分配自己的 ID。

所以同一个书签：

| | Chrome 本地 ID | 算出的云端 ID |
|---|---|---|
| 你的 Mac | `153` | `UUID-A` |
| 你的另一台机 | `287` | `UUID-B` |

云端于是有了 **两条记录指向同一个网址**。

#### 更糟的是：去重逻辑让它们开始互删

0.5.50 那次修复加了"同一网址只保留一条收藏位置，多余的标记删除"：

```367:380:src/lib/cloud-state.ts
  for (const binding of unbound) {
    if (
      !usedBookmarkItemIds.has(binding.bookmarkItemId) &&
      !protectedResourceKeys.has(binding.payload.resourceKey)
    ) {
      const unboundUrlKey = canonicalizeUrl(binding.payload.bindingHint.url);
      if (seenHintUrls.has(unboundUrlKey)) {
        deleted.push(binding);
        continue;
      }
```

于是发生了这样一个**无限循环**：

```
Mac 同步  →  看到云端有 UUID-B（不是自己的），网址重复  →  删掉 UUID-B，写入 UUID-A
另一台同步 →  看到云端有 UUID-A（不是自己的），网址重复  →  删掉 UUID-A，写入 UUID-B
Mac 同步  →  ……（无限重复）
```

**后果：**
- 每次同步都在产生大量写入和删除，change log 疯狂膨胀
- 每台机器都觉得"云端数据是错的，需要我修正"
- 你看到的现象就是：**同步永远做不完、改动传不过去、数据来回跳**

这一条是**双机用户的必然结果**。单机用户完全遇不到，所以以前的测试和修复都没发现。

#### 正确做法

云端 ID 必须**只由跨设备稳定的信息派生**。书签的跨设备稳定身份 = 规范化网址 + 所在文件夹路径：

```
bookmarkItemId = stableUuid("bookmark:" + resourceKey + "|" + folderPath.join("/"))
```

`resourceKey` 本身就是 `SHA-256(规范化 URL)`，两台机器算出来必然一样。这样：
- 两台机器算出**同一个 ID** → 云端自然 upsert，不会重复
- 不需要"按网址去重再删除"的补丁逻辑 → ping-pong 循环消失
- 顺便支持"同一网址放在多个文件夹"（现在被强行去重掉了，其实是能力损失）

### 1.3 R2 + R3：换封面必然失败的死循环

#### R2：资产 ID 里混进了内容哈希

```179:179:src/lib/cloud-assets.ts
  const assetId = await stableAssetId(`${input.identity}:${digest}`);
```

`digest` 是图片内容的 SHA-256。意味着：**图片内容一变，assetId 就变。**

但服务端是按 `(resource_key, asset_kind)` 来管理"这个书签的封面"的。你换封面时：
- 客户端拿着**新 assetId** 去登记
- 服务端发现这个位置已经有一条 ready 的记录（旧 assetId）
- 或者反过来，新 assetId 命中了一条历史残留记录，但 object_key 不同
- → **409 The asset identifier is already bound to different content**

这就是 0.5.60 记录的"181 条 assetId 与内容不匹配"。那不是历史脏数据造成的，那是**这个 ID 设计的必然产物**——每换一次封面就制造一条。

**正确做法：** assetId 只由位置派生，不含内容哈希：

```
assetId = stableAssetId(identity)   // 例如 "cover:<resourceKey>"
```

内容变化通过 `sha256` 字段表达，服务端按 assetId **覆盖更新** object_key / sha256 / byte_size。这才是"替换封面"的正常语义。

#### R3：修 409 的补丁本身有 bug —— 这就是修不好的 422

0.5.60 加了一段"遇到 409 就换随机 ID 重试"的防御代码。请看完整流程：

```200:229:src/lib/cloud-assets.ts
  let upload;
  try {
    upload = await requestUpload(assetId);
  } catch (error) {
    if ((error as { status?: number }).status === 409) {
      upload = await requestUpload(crypto.randomUUID());
    } else {
      throw error;
    }
  }
  const headers = new Headers(upload.headers);
  headers.delete("content-length");
  const response = await fetch(upload.uploadUrl, {
    method: "PUT",
    headers,
    body: new Blob([exactArrayBuffer(bytes)], { type: mimeType }),
    signal: AbortSignal.timeout(60_000)
  });
  if (!response.ok) throw new Error(`图片上传失败（${response.status}）。`);
  const completed = await cloudRequest<{ revision: number }>(
    `/v1/assets/${assetId}/complete`,
    ...
  );
  input.state[input.identity] = { assetId, sha256: digest, revision: completed.revision };
```

**`crypto.randomUUID()` 生成的新 ID 没有被赋值给任何变量。**

结果：
1. 用**新 ID** 向服务端登记上传，拿到新 ID 对应的上传地址
2. 把图片 PUT 到**新 ID** 的对象位置
3. 然后拿**旧 assetId**（`const`，从没变过）去调 `/v1/assets/{旧ID}/complete`
4. 服务端去检查**旧 ID** 对应的那个对象——那个位置要么是空的，要么是别人的旧内容
5. sha256 / 大小校验必然失败 → **422 Uploaded asset failed size, digest, or server-side encryption verification**
6. 本地 `state` 记录的还是旧 assetId，下次对账继续错

**这就是 0.5.61 和 0.5.62 一直在追但没抓到的 422。** 那两轮修复分别去改了 COS 的 `x-cos-metadata-directive` 和服务端删除任务竞态——都是在服务端找原因，而真正的 bug 在客户端这 6 行里。服务端改动本身没错（元数据 Replace 是对的），但它治不好这个病。

修好 R2 之后 409 就不会发生，R3 这段代码本应直接删掉；作为过渡期防御保留的话，必须把新 ID 正确传递下去。

## 2. 站点标识与封面

### 2.1 先纠正一个认知：现在有 5 套图片状态，不是 2 套

你说的是"两块用户可定制的东西"，但实现上它们分散成了 5 个独立数据源：

| # | 数据 | 存储位置 | 用在哪 |
|---|---|---|---|
| 1 | 站点标识 | IndexedDB `siteBrands`，按 host | 侧边栏列表小图标 |
| 2 | 页面快照 | IndexedDB `pageSnapshots`，按 canonicalUrl | 网页端瀑布流大卡片 |
| 3 | 代表图 | `resource.thumbnailDataUrl`，按 resourceKey | 侧边栏缩略图 |
| 4 | og:image 网址 | `resource.imageUrl`，字符串 | 扫描时的输入 |
| 5 | 内置兜底图 | 打包的 40 张 WebP | 前面全失败时 |

**它们的主键都不一样**（host / canonicalUrl / resourceKey），互相之间没有一致性保证。你右键设一次封面，代码要**同时写两个 store**（`resource.thumbnailDataUrl` 和 `pageSnapshots`），漏一个就会出现"侧边栏有、网页端没有"或者反过来。

这就是"不稳定"的结构性来源。

### 2.2 为什么会"丢失"

我一共找到 12 个会让封面消失的代码路径，最重要的几个：

| 原因 | 位置 | 说明 |
|---|---|---|
| 快照上限 2000 条，超出按时间删最旧 | `storage.ts:448-464` | 静默丢失，用户无感知 |
| canonicalUrl 是快照主键 | `storage.ts` | URL 规范化规则一改，所有旧快照全部对不上 |
| "同图多网址"清理任务 | `background.ts:7977-7989` | 每次 SW 启动就跑，误判会整组删 |
| 云端恢复反向覆盖 | `cloud-assets.ts:392-417` | 时间戳比较不可靠时会用云端旧图盖掉新图 |
| 同 host 多页共用 og:image 时清空 | `background.ts:6097-6103` | banner 检测的副作用 |
| 用户自定义封面**没有保护标记** | 全局 | **最关键**：自动逻辑不知道这张图是用户手动设的，会当成普通图覆盖 |

**最后一条是核心。** 现在的数据结构里没有"这是用户手动设置的"这个标记（`origin: 'user' | 'auto'`），所以任何自动逻辑都有权覆盖它。你辛苦右键设的封面，随时可能被一次自动截图、一次云端恢复、一次去重清理干掉。

### 2.3 为什么"加载好半天才出来"

网页端瀑布流的加载方式是**一张卡片一次消息往返**：

```124:168:src/ui/manager/components/LibraryCardCover.tsx
  // IntersectionObserver → sendExtensionRequest({ type: "GET_PAGE_SNAPSHOT", canonicalUrl })
  // → setSnapshotImageUrl(snapshot?.imageDataUrl)
  // → <img loading="lazy" src={dataURL} />
```

具体问题：

1. **N 次独立消息往返**：50 张卡片 = 50 次 `chrome.runtime.sendMessage`，每次都要 Service Worker 响应。没有批量接口。
2. **传的是 dataURL**：一张 960×600 的 WebP 转成 base64 后约 60–120KB 的**字符串**，要在 Service Worker 和页面之间做结构化克隆序列化。50 张就是 3–6MB 的字符串搬运。
3. **主线程解码**：`<img src="data:image/webp;base64,...">` 的解码在主线程，连续几十张会明显卡顿。
4. **滚出视口就清空**：

```138:143:src/ui/manager/components/LibraryCardCover.tsx
  // !nearViewport 时 setSnapshotImageUrl("")
```
   滚回来要重新走一遍完整流程，先闪兜底图再闪回封面。

**修复方向：**
- 用 **Blob + `URL.createObjectURL()`** 代替 dataURL（体积省 33%，传输是零拷贝，解码走浏览器原生路径）

### 2.6 我的整体建议：把 5 套合并成 1 套

## 4. AI Agent

### 4.1 现状：它不是一个 Agent，是一条固定流水线

你的判断"实现比较粗浅、能力受限"是准确的。让我说得更具体：

现在的架构是**四步固定管道**，每步调一次大模型，返回 JSON 后本地解析：

```
用户提问
  → [可选] 全库分批筛选（每批 60 条，5000 条书签 = 84 次 API 调用）
  → 本地关键词检索召回 80 条
  → 让模型输出"思考步骤"（一次调用）
  → 让模型输出"回答 + 操作列表"（一次调用）
  → 本地校验 → UI 确认 → 执行
```

**关键缺失：没有使用任何一家的 function calling / tools API。**

"工具"是用**自然语言写在 prompt 里**的 JSON 格式说明，指望模型自己按格式填。三家服务商都只用了最基础的 `response_format: json_object`，这只保证"输出是个 JSON 对象"，**不保证字段结构**。

```477:492:src/lib/local-ai.ts

        model,
        messages: [
          { role: "system", content: JSON_ONLY_SYSTEM_INSTRUCTION },
          { role: "user", content: prompt }
        ],
        response_format: { type: "json_object" },
```

### 4.2 "格式不对然后失败"的真正原因

不是模型不行，是**用错了 API**。

OpenAI 和 Gemini 都支持**严格结构化输出**：
- OpenAI：`response_format: { type: "json_schema", json_schema: { strict: true, schema: {...} } }`
- Gemini：`generationConfig.responseSchema` + `responseMimeType`

开启 strict 模式后，模型**在解码层面就被约束**只能生成符合 schema 的 token，格式错误率接近零。

而现在的做法是"让模型自由发挥，然后本地写正则修补"：

```238:299:src/lib/local-ai.ts
function repairJsonStringNewlines(...)
  // 修复字符串内换行
  // 去除 // 和 /* */ 注释
  // 去除尾逗号
```

这套修补逻辑已经积累了三轮补丁（0.5.51、0.5.52 都在改它），**方向从一开始就是错的**。用 strict schema 之后这些代码全部可以删掉。

其他稳定性问题：
- 全库扫描**任何一批失败，整次查询就失败**（`local-ai.ts:952-964`），5000 条书签要成功 84 次才能出结果
- 没有流式输出，45 秒超时，长回答容易踩线
- 思考阶段只重试 1 次，回答阶段 2 次，都失败就直接报错给用户

### 4.3 能力边界：能改，但很受限

Agent **确实能真改书签**，有 9 种操作，有确认环节，有 30 天撤销。这块基础是好的。

但能力形态是"**一次性提交最多 40 项操作**"，不能：

| 你想要的 | 现在能不能 |
|---|---|
| "把所有书签按你推荐的方式完全重排" | ❌ 不能。需要先建几十个文件夹再移动几百条，远超 40 项上限，且模型没有"先建文件夹再移动"的多步执行能力 |
| "批量改所有书签的名称" | ❌ 不能。update_bookmark 是单条，一次 40 条，几百条要手动重复十几轮 |
| "先分析一下我的书签结构，再决定怎么整理" | ❌ 不能。模型只能看到一次性喂进去的 80 条摘要，不能主动"再查一下某个文件夹" |
| "把重复的合并掉" | ⚠️ 半能。有一套独立的规则引擎（`library-insights.ts`）能算重复，但 **Agent 调用不到它** |
| 跨会话继续上次的整理 | ❌ 没有任务持久化 |

**根本限制：模型只能"说"，不能"查"。** 它拿到的是一次性打包的上下文，不能像真正的 agent 那样"我先看看文件夹结构 → 再查一下这个文件夹里有什么 → 然后决定移到哪"。

### 4.4 升级方案：改成真正的 tool-calling agent

需要做四件事：

**（1）定义真正的工具，用原生 API 传给模型**

只读工具（模型可以随便调，不需要确认）：
```
list_folders()                              → 完整文件夹树 + 每个文件夹的条目数
search_bookmarks(query, limit, filters)     → 搜索
get_bookmarks(ids[])                        → 批量取详情
get_folder_contents(folderId, cursor)       → 分页读文件夹内容
get_library_stats()                         → 总数、重复、死链、无标签数量等
find_duplicates() / find_dead_links()       → 接上现有的 library-insights 规则引擎
```

写工具（产出提案，不直接执行）：
```
plan_create_folders(specs[])
plan_move_bookmarks(moves[])       ← 支持 500+ 条
plan_rename(renames[])
plan_delete(ids[], reason)
plan_update_metadata(updates[])
```

**（2）多轮循环**

模型可以连续调用工具，最多 N 轮（建议 12 轮），每轮结果喂回去。这样它能"边查边想"。

**（3）大批量操作走"计划书"模式**

模型不再直接返回 40 条操作，而是返回一个**结构化计划**：

```
计划：重排为 8 个主题文件夹
├─ 新建 8 个文件夹
├─ 移动 342 条书签
├─ 删除 12 条重复
└─ 保持不动 47 条
```

执行时分批提交（每批 50 条），带进度条，可中途取消，全程一个撤销批次。

**（4）严格结构化输出 + 流式**

- 用 zod 定义 schema → 转成 JSON Schema → 传给 OpenAI strict / Gemini responseSchema
- 回答部分走流式，边生成边显示

**关于工具执行的安全边界：** 只读工具自动执行；写工具一律先产出计划，用户确认后才动 Chrome。破坏性操作（删除）在计划里单独标红并默认不勾选。这条不能省。

4. **数字优先于形容词。** 能显示 `12/48` 就不要写"正在处理中"。
5. **一个页面最多一个主按钮。**
6. **禁止 `variant="unstyled" + className="button"` 的双轨写法**（可用脚本检测）。

- 每次修改都可能踩到不相关的逻辑
- 多个 agent 并行工作必然冲突
- 我在审计时发现的几个 bug（比如 409 那段），本质上是"改的人看不到全貌"

**建议：把这两个文件拆开，作为所有后续工作的前置条件。** 不拆的话，后面每一轮修复都会继续制造新问题。

### 6.2 缺少跨设备的自动化测试

现在的测试（343 项）全是单机单进程的。而你遇到的**全部严重问题都是双机场景**。

建议加一类"双客户端集成测试"：在同一个测试里模拟两个设备实例（不同的本地 Chrome ID、不同的 storage），对同一个测试服务器做读写，断言最终一致性。这类测试能直接抓住 R1 那种 ping-pong。

**没有这个，同样的问题一定会再回来。**

### 6.3 版本号推进太快，每次都是"修了又坏"

从 0.5.49 到 0.5.62，13 个版本全部是 bugfix，而且相当一部分是在修上一个 bugfix 引入的问题（0.5.50 的去重引入了 ping-pong，0.5.60 的 409 防御引入了 422）。

这是典型的"在错误的抽象层上打补丁"。建议这一轮**不要继续打补丁**，而是按第 7 节的顺序做结构性修复。

### 6.4 服务端有能力但客户端没用

服务端已经实现了完整的墓碑机制、冲突版本表、change log、幂等操作缓存——**这些都是对的设计**。问题全在客户端没有正确使用它们。

好消息是：**这一轮基本不需要改服务端**（除了 asset 的 upsert 语义要放宽）。工作量比看起来小。

### 6.5 关于"每次版本更新都要重新加载好久"

这个现象还有一个你可能没意识到的成因：`dist/` 里的资源文件名带内容哈希（`sidepanel-BqIBqn_l.js`）。每次构建哈希都变，Chrome 会把它当全新文件重新加载和解析，**没有任何缓存复用**。

这在扩展场景下是必然的，但可以通过"把不常变的代码（React、Radix）拆成独立 chunk"来减轻——它们的哈希不变，Chrome 就能复用。

## 7. 建议的执行顺序

我把工作分成 6 个阶段，**顺序不能乱**，因为后面的依赖前面的。

| 阶段 | 内容 | 为什么是这个顺序 | 预估 |
|---|---|---|---|
| **P0** | 修 4 个根因 bug（R1–R4）+ 封面 capturedAt | 你现在**每天都在受影响**，且改动量最小、风险最低 | 1–2 天 |

| **P2** | 同步引擎重写（统一状态机 + 实时进度 + 删除墓碑） | 依赖 P0 的 ID 修复和 P1 的拆分 | 3–4 天 |
| **P3** | 视觉资产统一（`visuals` store + Blob + origin 标记） | 依赖 P2 的同步引擎 | 3–4 天 |

| **贯穿** | 启动性能优化 | 拆成小项，跟在各阶段后面顺手做 | — |

## 8. 哪些必须由我来做

大部分工作可以交给执行 agent，但以下几项建议由我（或同等能力的模型）亲自做：

| 项目 | 原因 |
|---|---|
| **R1 的 ID 迁移方案** | 改 ID 生成规则意味着**云端现有的 235 条收藏位置全部会变成孤儿**。需要设计一次性迁移：读旧记录 → 按新规则重算 ID → 写新记录 → 删旧记录，且要保证两台机器同时跑也不出错。这个迁移写错一次就会丢数据，且不可逆。 |
| **拆分 background.ts** | 9184 行拆分需要完整理解模块间的隐式依赖（共享的模块级变量、监听器注册顺序、SW 生命周期约束）。低能力 agent 拆会拆出循环依赖和监听器丢失。 |
| **同步状态机设计** | 需要同时推理并发、重入、离线、时钟偏差、多设备竞态。这是纯设计工作，写错的代价是又一轮"修了又坏"。 |
| **Agent 工具集的 schema 设计** | 工具粒度和 schema 设计直接决定模型能不能用好。设计错了，后面写多少代码都没用。 |
| **双设备一致性测试的设计** | 需要构造真正能复现 ping-pong 的场景，不是简单的 CRUD 测试。 |

其余的（写具体实现代码、删文案、CSS 收敛、性能优化、补测试）都可以交给执行 agent，PRD 里已经写到了可以照抄的粒度。

## 9. 需要你决策的问题

1. **是否接入 Google S2 / DuckDuckGo favicon 服务？** 能大幅降低兜底率，代价是向第三方发送域名，与现有隐私文案冲突。（我建议：接，默认开，设置里可关，隐私页如实说明）
2. **同步范围默认值改成"完整备份"？** 现在默认是"仅文字"，但用户装这个产品的核心价值就是跨机看到封面。
3. **`bookmarkItemId` 迁移的处理方式**：是「清空云端收藏位置表，让两台机器重新上传」（简单、快、但会短暂丢失云端的备注冲突历史），还是「写一次性迁移脚本原地转换」（复杂、慢、但无损）？（我建议：前者。这张表的内容本来就是从本地重建的，没有独有数据）
4. **是否接受 `background.ts` 和 `SidePanelApp.tsx` 的大拆分？** 这会产生一个很大的 diff，且短期内不新增任何功能。
