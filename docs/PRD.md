## 0. 使用约定

### 0.1 并行开发协调

同时可能有多个 Agent 在这个仓库工作。领取需求前先在 `AGENT_PROGRESS.md` 的「暂不应并行修改」小节登记你要独占的文件，完成后移除。

`src/extension/background.ts` 和 `src/ui/sidepanel/SidePanelApp.tsx` 是两个高冲突文件（分别 2,227 行和 2,815 行）。同一时间只允许一个 Agent 修改其中任意一个，且必须在进展文档登记。

云端相关文件（`src/lib/auth.ts`、`src/lib/cloud.ts`、`src/lib/supabase.ts`、`supabase/`）由 F14 独占改造，M1 / M2 的其他需求不要触碰。

### 0.2 每个需求的完成定义

一个需求只有同时满足下列四条才算完成：

1. `npm run check` 在 Node.js 22.22.2 下全绿（类型检查 + 测试 + 生产构建）。
2. 新增逻辑有对应的单元测试，测试数量在进展文档中更新。
3. 在真实 Chrome 中加载 `dist/` 完成人工验收，而不是只在 `?preview=1` 开发预览里验证。
4. `AGENT_PROGRESS.md` 记录了实际改动、验证方式和已知边界。

### 0.3 需求编号约定

编号一经分配不再变动，新增需求顺延取号。需求归属哪个里程碑以第 3 章的里程碑表为准，不看编号顺序。这样后补需求不会导致全文档重编号，也不会让已经在进行中的任务失去引用。

### 0.4 术语

| 术语 | 含义 |
| --- | --- |
| 原生层 | `chrome.bookmarks` 中的标题、URL、文件夹结构。唯一事实来源。 |
| 智能层 | Aarre 存在本地 IndexedDB 的摘要、标签、主题、封面等元数据。 |
| 资源键 | `SHA-256(规范化 URL)`，智能层的主键，跨设备稳定。 |
| BYOK | 用户自带 AI API Key，请求由扩展直接发往服务商。 |

## 1. 产品定位与不可动摇的原则

Aarre 是 Chrome 原生书签的增强层，不是又一个书签服务。

下面四条是产品的地基。任何需求如果和它们冲突，改需求而不是改原则。

1. **Chrome 是标题、URL、文件夹的唯一事实来源。** 智能层可以读、可以关联、可以建议修改，但不允许用任何副本覆盖原生层。用户卸载 Aarre 后，书签必须一根毛都不少。
2. **资源键用规范化 URL 的哈希，不用 Chrome bookmark ID。** bookmark ID 跨设备不稳定，这是多设备合并唯一可靠的锚点。
3. **网页正文不经过 Aarre 自己的服务器。** BYOK 请求由扩展直连服务商。这是隐私叙事的根基，也是成本结构能成立的原因。
4. **完整增强能力必须具备稳定权限。** `<all_urls>` 作为必需 `host_permissions`，在安装/升级时由 Chrome 明示。原因是 Chrome 自带星标不会授予 `activeTab`，且 `captureVisibleTab()` 对持久权限要求真正的 `<all_urls>`；业务逻辑仍只处理 HTTP(S) 收藏。运行时只在新收藏、已收藏页面补缺/7 天静默刷新或用户主动扫描时使用，不把持续权限解释成持续监控。

## 2. 目标用户与核心场景

### 2.1 主要用户

**重度收藏者**：Chrome 书签在 300 条以上，文件夹结构已经失控，知道自己收藏过某个东西但找不到。技术从业者、研究者、设计师占多数。

这批人的关键特征是：他们**已经有大量存量书签**，所以「零迁移成本」对他们的价值远高于任何新功能。这也是 Aarre 相对所有平行库产品的结构性优势。

### 2.2 三个核心场景

| 场景 | 用户心智 | 当前状态 |
| --- | --- | --- |
| 找回 | 「我记得收藏过一个讲 X 的东西」 | 断路。侧边栏没有搜索框，只能问 AI 或手动翻文件夹。 |
| 收藏 | 「这个先存着，以后可能用得上」 | 基本可用。右键和星标都通，AI 摘要标签能生成。 |
| 整理 | 「我的收藏夹一团糟，但我不知道从哪下手」 | 缺失。这是最大的机会，见 M2。 |

## 4. M1 · 补断口

### 收藏入口与完整增强层（2026-07-31 定稿）

Chrome 原生书签是唯一事实来源。Aarre 无法可靠判断一条书签最初是由扩展还是 Chrome 自带星标创建，因此交互只看“当前 URL 是否已收藏”，不显示来源。

- 当前页面右键项随活动 tab、URL 和书签事件同步：无匹配为“添加到收藏…”，有匹配为“管理此收藏…”；查询失败时禁用入口。Chrome Context Menus API 不提供菜单显示前的链接目标事件，因此链接项固定使用“添加或管理此链接…”的中性文案，点击后再精确校验。
- 完全相同且只有一条时更新原记录；canonical-only 命中让用户确认复用或另存；多条命中展示文件夹位置并要求选择；受管理记录仅更新 Aarre 增强元数据。
- Chrome 自带星标新增的书签由 `bookmarks.onCreated` 自动进入增强队列，不要求用户再点一次 Aarre 收藏，也不创建第二条记录。
- 完整增强由 **AI 摘要、标签、真实页面截图** 三部分组成，不提供拆掉其中一项的保存选项。原生书签先可靠保存；权限、AI Key、网络或前台页面暂不可用时，任务持久保留并退避重试。
- Chrome 自带星标不会给扩展 `activeTab`，因此不能承诺三项在点击星标的同一瞬间全部完成。原生书签先成功，AI 与截图任务持久等待；页面仍在合适前台时自动继续，否则在该收藏下次通过 Aarre、地址栏或普通链接打开并稳定后补齐，不增加“手动截图”动作。
- 内部、无痕、银行、支付、医疗、内网及用户排除网站不读取正文、不调用 AI、也不截图，以随扩展打包的 Aarre 兜底图呈现；这是隐私豁免，不允许用普通 `og:image`、网络代表图或生成图冒充真实网页截图。

### 网页端收藏库（2026-07-31 定稿）

- Tab 上方只保留一行 Aarre 品牌标识；删除大标题、说明、“返回侧边栏”、“仅保存在本机”和账号状态等冗余内容。
- 搜索框属于收藏库，只搜索收藏标题、标签、摘要与 Chrome 文件夹；输入草稿不应提前改变结果，提交后才更新结果、高亮、排序和 URL。状态、文件夹、排序与查询可组合并在刷新后恢复。
- 瀑布流大封面优先使用 `pageSnapshots` 中的真实网页截图。无可信截图时使用 40 张本地 Aarre 兜底封面：可靠语义分类优先，否则按 canonical URL 稳定哈希分配；同一收藏刷新、筛选或排序后不跳图。不得使用侧边栏分类封面、普通 `og:image`、网络代表图或低清 favicon 作为大封面。
- 每张卡片提供“编辑”入口，可修改单个 Chrome 收藏位置的名称、完整 URL、文件夹，以及 Aarre 自定义标签和备注；AI 摘要只读。多位置必须先明确选择；删除仅删除所选位置并提供二次确认及 30 天恢复。受管理收藏只允许修改 Aarre 元数据。
- URL 只发生追踪参数、普通 hash、尾斜杠、已知 canonical 或重定向 alias 变化时，必须把完整地址写回 Chrome，但保持同一资源、其他收藏位置、AI 和截图不变。真正跨站时只迁移所选绑定，旧站 AI/截图不得沿用，并在新网页下次稳定打开时重新增强。

### F1 · 侧边栏搜索

**要解决什么问题**

找书签是这个产品第一高频的动作，但现在只有两条路：手动展开文件夹树，或者问 AI（要配 Key、要等几秒、要花钱）。关键词搜索这条最基础的路径完全是断的。带搜索的 `manager.html` 存在，但侧边栏没有任何入口能进去，等于白做。

**怎么做**

侧边栏标题行下方常驻一个搜索框，三段式响应：

1. **输入即过滤（0 延迟，纯本地）**：实时过滤当前书签树，命中项高亮，命中项所在的父文件夹自动展开，未命中的分支折叠隐藏。搜索范围包括标题、URL、AI 标签、AI 摘要、用户备注。
2. **回车升级为语义检索**：用 F8 的本地混合检索重排结果，按相关度平铺展示（不再保持树形），每条显示所在文件夹路径。
3. **搜索框内的次级动作**：结果为空时显示「让 AI 帮我找」按钮，一键把当前输入转成 Agent 提问。

清空输入立即回到原书签树，且恢复搜索前的展开状态和滚动位置。

**验收标准**

- 在 1,000 条书签的样本下，输入过滤的首帧响应在 100ms 以内。
- 搜索「机器学习」能命中标题里只有「Machine Learning」但 AI 标签含「机器学习」的书签。
- 清空搜索后书签树的展开状态和滚动位置与搜索前一致。
- 搜索状态下按 Esc 清空输入而不是关闭侧边栏。

**技术备注**

过滤逻辑不要每次都遍历全树重建。在 `SidePanelApp.tsx` 里对 `visibleBookmarkNodes` 建一次扁平索引并缓存，输入变化时只做索引查询。检索算法复用 F8 的实现，不要在这里另写一套。

### F2 · 撤销栈与回收站

**要解决什么问题**

Agent 一次能执行 8 项操作，包括 `delete_folder` 连带删除整个文件夹的全部内容。执行后用户只能靠 Chrome 手动恢复——而 Chrome 并没有书签回收站。一次误确认就是永久损失。

在补上撤销之前，「让 AI 整理书签」这件事在道义上就不该向用户推广。这是 M2 主动整理提案的前置条件。

**怎么做**

**执行前快照。** `executeBookmarkAgentActions` 在调用任何 `chrome.bookmarks` 写方法之前，把受影响的节点完整序列化（含子树、父 ID、index、标题、URL）写入新的 IndexedDB store。删除类操作必须递归快照整棵子树。

**撤销入口有两处：**

- 聊天里执行结果卡片下方常驻「撤销这批操作」按钮，30 天内有效。
- 设置页新增「最近的更改」列表，按批次展示，每批可单独撤销。

**回收站。** 用户手动删除的书签也进快照 store，设置页可查看和恢复，保留 30 天后自动清理。

**撤销的语义要诚实。** 撤销是「反向重建」而不是真正的时间回溯：被删除的书签会以相同标题、URL、父文件夹、index 重新创建，但 Chrome 会分配新的 bookmark ID。因为智能层用的是 URL 哈希做主键，所以摘要、标签、封面会自动重新关联上——这一点要在 UI 上说明，避免用户以为数据丢了。

如果撤销时目标父文件夹已经不存在，就重建到主书签栏根目录，并在结果里明确告知。

**验收标准**

- 删除一个含 20 个书签的文件夹后撤销，20 个书签全部回到原位置、原顺序，且 AI 摘要和标签仍在。
- 撤销一批含 5 项操作的提案，5 项全部回滚；其中 1 项因目标已被用户手动改动而无法回滚时，其余 4 项仍成功，UI 逐条说明结果。
- 30 天前的快照在扩展启动时被自动清理。
- 快照写入失败时，操作**拒绝执行**而不是继续——不能有无法撤销的写入。

**技术备注**

IndexedDB 需要从 v1 升到 v2，新增 `undoSnapshots` store（keyPath: `batchId`，索引 `by-created-at`）。升级函数必须保留现有 `resources` 和 `outbox` 的数据，不能重建数据库。`src/lib/storage.ts` 里的 `openDB` 版本号和 `upgrade` 回调要一起改。

**store 名字叫 `undoSnapshots` 而不是 `snapshots`**，因为 F22 的页面快照会用 `pageSnapshots`，两者含义完全不同，同名会造成严重误读。

### F4 · 首次使用引导

**要解决什么问题**

底部 Agent 输入框永远可用。新用户输入问题、等待、然后收到「请先在设置中填写 API Key」。第一次使用就撞墙，这是新用户流失率最高的位置。

同时，一个刚装上 Aarre 的用户看到的是自己原本的书签树，和 Chrome 原生书签管理器没有区别——他感受不到任何 AI 价值，因为扫描要手动去设置页启动。

**怎么做**

**首次安装引导（三步，可跳过）：**

1. 说明 Aarre 直接用你现有的 Chrome 书签，不需要导入、不会改动。
2. 选 AI 服务商并填 Key。这一步提供「先跳过，只用书签管理」的出口。
3. 显示「你有 1,240 条书签，扫描预计 18 分钟、约 ¥3.2」，提供「现在扫描」和「以后再说」。

**未配置 AI 时的输入框状态。** 输入框不再是可输入的普通状态，而是变成引导态：显示「配置 AI 后可以直接问你的收藏」，点击直达设置页 AI 区块。这比让用户先输入再报错要好得多。

**扫描进行中的可见性。** 扫描不应该只在设置页可见。侧边栏标题行显示一个细进度条，点击进入设置页详情。

**验收标准**

- 全新安装后打开侧边栏，看到的是引导而不是空的书签树。
- 未配置 Key 时点击底部输入框，直接跳转设置页，不产生任何失败请求。
- 跳过引导的用户不会被反复打扰，但设置页保留重新启动引导的入口。

### F5 · UI 收敛

**要解决什么问题**

`manager.html` 有搜索、语义检索、状态筛选、卡片视图，功能不弱，但侧边栏没有任何入口指向它。绝大多数用户会永远不知道它存在。现在这个状态是最差的：维护两套 UI，用户只用得到一套。

**怎么做**

明确分工，二选一：

**方案 A（推荐）：保留全页，明确分工。** 侧边栏做「快速取用」——找、开、收藏、问。全页做「批量整理」——多选、批量打标、批量移动、整理提案预览、周报。侧边栏右上角加入口，且在整理提案（F7）产生时主动引导用户去全页处理。

**方案 B：砍掉全页。** 把语义检索合并进侧边栏搜索，`manager.html` 只保留为 AI 整理提案的展示页。

选 A 的理由是 M2 的整理提案和 M4 的周报都需要更大的画布，侧边栏 400px 宽装不下。

**验收标准**

- 侧边栏能进入全页，全页能回到侧边栏语境（至少有明确的说明）。
- 两处的书签数据、AI 元数据、封面完全一致，不存在只在一处生效的能力。

### F6 · 状态持久化与会话管理

**要解决什么问题**

一批小问题，单个都不致命，但每天都在磨损体验。

**怎么做**

| 项 | 现状 | 改为 |
| --- | --- | --- |
| 文件夹展开状态 | 每次重开全部折叠 | 存 `chrome.storage.local`，重开恢复 |
| 滚动位置 | 每次回到顶部 | 记住上次位置 |
| 会话删除 | 后台有 `DELETE_AGENT_CONVERSATION` 但无 UI 调用 | 历史列表支持删除和重命名 |
| 会话上限 | 50 个之后行为不明确 | 超出时按最后更新时间淘汰，并在 UI 说明 |
| 失败恢复 | 书签树加载失败后只有一条可关闭的错误 | 加「重试」按钮 |

**验收标准**

- 展开三层文件夹后关闭再打开侧边栏，展开状态完全一致。
- 删除一个历史会话后重开侧边栏，它不再出现。

### F22 · 悬浮预览

归属 M1。编号顺延，不代表优先级低于 F7 及之后的需求。

**要解决什么问题**

48px 的标识只能回答「这是哪个站点」，回答不了「这条书签具体是什么」。用户在列表里扫过时经常需要确认「是不是我要找的那一条」，现在只能点开——一旦点错就跳走了页面，还要退回来。

悬浮预览把「确认」这一步的成本从「打开一个网页」降到「停留半秒」。

**先说清楚一件做不到的事**

需求里希望「实时抓取 HTML 去展现内容」。**这条路是结构性堵死的，不是工程难度问题**，有三个原因：

1. 绝大多数正经站点都设置了 `X-Frame-Options: DENY` 或 CSP 的 `frame-ancestors`，iframe 会被浏览器直接拒绝加载。Google、GitHub、大部分主流站点都在此列。
2. 即使某个站点允许 iframe，在扩展页面里渲染任意外站 HTML 是严重的安全问题。
3. 每次 hover 触发一次真实页面加载，性能和隐私都无法接受。

所以预览必须基于**已缓存的页面快照**。这确实是一个妥协：能预览的书签只有攒下过快照的那些。下一节说明为什么这个妥协可以接受，以及怎么让快照库尽快铺开。

**核心判断：悬浮层只回答「这个页面长什么样」，不承担任何信息展示职责**

> **2026-07-30 修订。** 本节此前的方案是「预览窗主体是信息区，快照是上方的补充，没有快照时退化为纯信息卡」。产品负责人依据安装版实机截图判定：信息区在 hover 场景下是噪音——用户真正需要的只有页面画面本身，标题和文件夹路径在书签行上已经能看到，摘要和标签属于点开后的阅读场景。**方案改为：悬浮层只有一张页面快照，没有信息区，没有角标，没有快照时不出现任何东西。** 下文按新方案重写，被替换的论证不再保留，避免后来的 Agent 读到自相矛盾的依据。

这个取舍的代价是明确的、已被接受的：

- **刚安装的用户在积累出快照之前，hover 不会有任何反馈。** 快照库会通过 Chrome 星标/Aarre 新收藏首拍，以及已收藏页面从 Aarre、地址栏或普通链接正常打开后的补缺与 7 天静默刷新自然长起来，所以这是一个随使用逐渐显形的功能，而不是装上就完整的功能。这一点在首次引导里说明即可，不作为缺陷处理。
- **不显示快照的采集时间。** 用户可能看到一张较旧的截图。当前版本选择“只补缺图、不因普通访问覆盖”，优先保证行为稳定且可预期；未来如需刷新，应提供明确策略，不能恢复无差别后台重拍。

**怎么做**

悬浮层宽约 340px，**内容只有一张 16:10 的页面快照**，外加卡片自身的边界和圆角。不放站点标识、站点名、标题、摘要、标签、文件夹路径、时间、快捷键提示或任何文字。

**没有快照时整个悬浮层不渲染**，不出现空卡、占位框、加载态或「暂无预览」之类的提示。hover 一条没有快照的书签，应当和没有这个功能一样安静。

**悬浮层不接收鼠标事件**（`pointer-events: none`），点击、滚轮、拖拽一律穿透到下层的书签列表。这是它能覆盖在列表上方而不干扰操作的前提。相应地，用户无法把鼠标移进悬浮层，也无法选中其中的内容——因为里面没有可选中的内容。

**为什么视觉区不用 `og:image` 或分类封面兜底**

这一条不因上面的修订而改变，反而更重要了：悬浮层现在**只剩**视觉区，它的全部可信度就建立在「这张图是这个页面的真实截图」上。

- `og:image` 是站点为社交分享准备的宣传卡，不是页面本身；分类封面是一张通用插画，关于这个具体页面什么信息都没有。放它们进去，用户会误以为看到了页面。
- 一旦悬浮层里可能是「真实的」也可能是「示意的」，用户就无法信任它，得先分辨再判断。**宁可什么都不显示，也不要一张需要用户先分辨真假的图。**

所以规则很简单：有快照就展示这张快照，没有就什么都不展示。

### 存量书签的快照怎么办

这是这个功能最实际的问题。用户装 Aarre 之前已经有几百上千条书签，那些页面从来没在 Aarre 面前打开过。

**先否掉一个方向：AI 批量分析生成不了截图。**

语言模型看不到网页，产出不了截图。图像生成模型能画一张「看起来像网页」的图，但那是凭空编造的——用户会以为那是真实页面，然后据此做判断。**这比没有截图糟糕得多，绝对不能做。** 悬浮层的全部价值建立在「这是真实的」这个前提上，一旦掺进生成图，整个功能的可信度就没了。

**再否掉一个方向：后台批量截图技术上堵死。**

这不是「不划算」而是「做不到」。`chrome.tabs.captureVisibleTab` 的名字就说明了它只能截取当前**可见**的标签页——后台标签页截不到。所以批量截图必须把每一个页面轮流切到前台，用户会看到浏览器疯狂闪烁几百次。唯一的绕法是 `chrome.debugger` + `Page.captureScreenshot`，但那会在页面顶部挂上「XXX 正在调试此浏览器」的黄条，而且 `debugger` 权限在 Chrome Web Store 审核中极为敏感，对一个书签工具来说完全不成比例。

**所以结论是：不能在后台无感批量截图，但可以提供用户明确启动的前台逐页补拍。**

按新方案，「没有快照」等于「这条书签暂时没有悬浮预览」。这不构成缺陷，但确实意味着**功能的可用范围完全等于快照库的覆盖范围**，所以把快照库尽快铺开比之前更关键。

用户主动选择「补齐缺失封面」后，Aarre 可以创建一个专用标签页，在该标签页保持前台时逐个打开缺图收藏，仍然复用字体、首屏图片、DOM 稳定和最终 URL 校验，再以单并发完成截图。用户切走标签、切换窗口或把 Chrome 放到后台时任务必须进入等待，不得自动抢回焦点；任务支持暂停、继续和取消。这个流程是**可见、显式、可中断的前台任务**，不是后台截图。它只补页面快照，不顺带触发全库 AI 请求或消耗用户 AI 额度。

**快照库通过正常收藏和浏览自然长起来。** 采集规则如下：

| 时机 | 说明 |
| --- | --- |
| Chrome 星标或 Aarre 新收藏当前页 | 基础收藏数据落库后立即排队；确认页面已加载完成并稳定后静默首拍 |
| **已收藏且缺图的网页以任意正常方式打开** | Aarre、地址栏、Chrome 书签栏、历史记录或普通链接都进入同一补拍协调器；页面稳定后补拍，成功时显示 toast“封面截图已更新” |
| **已收藏且有图的网页正常打开** | 未满 7 天不处理；距上次采集满 7 天后静默刷新，不显示 toast |
| **用户主动批量补齐缺失封面** | 在专用前台标签页中单并发逐页加载和截图；失焦即等待，可暂停、继续或取消，不触发 AI 扫描 |

普通浏览只做当前 URL 的本地收藏命中，不扫描全库。命中缺图收藏时自动补拍；已有图按 7 天新鲜度静默刷新，因此不会因每次访问反复截图。

**采集属于完整增强层的必选步骤。** 不再保留隐藏或容易误触的全局关闭值；否则 Chrome 原生收藏会出现“收藏成功但增强层永久不完整”的不可解释状态。隐私保护通过无痕拒绝、敏感/内网页面同时拒绝 AI 与截图、只处理已收藏页面和快照永不上云实现。

隐私边界必须同时到位，否则「默认开启」站不住：

- 仅 `http/https`，Chrome 内部页和本地文件跳过。
- 无痕窗口完全不采集。
- 内置一份不采集的域名清单（银行、支付、医疗、内网地址）。
- **快照永不上传云端**，只存在本机（见 F14）。
- 首次引导和隐私政策里明确说明这个行为，不能让用户事后才发现。

首次引导的措辞建议是「打开已收藏网页时，Aarre 会在页面稳定后自动补齐预览截图，越用越完整」。

**过期快照的处理。** 快照会随站点改版失效，但**不在悬浮层上标注采集时间**（2026-07-30 修订，理由见本节开头）。`snapshotAt` 记录在 IndexedDB；正常浏览时只在截图距上次采集满 7 天后静默刷新，不向用户显示时间，也不在每次访问时覆盖。

**交互细节**

| 项 | 规格 | 理由 |
| --- | --- | --- |
| 触发延迟 | 400ms | 1–2 秒太久，用户已经移开了。行业惯例是 300–600ms |
| 意图检测 | 鼠标移动速度高于阈值时不计时 | 快速划过列表不应该触发，只有真的停下来才算。**注意判定方向：速度低于阈值才开始计时，写反会变成「划得越快越容易弹出」** |
| 消失延迟 | 移出后 200ms | 避免在相邻两行之间移动时闪烁，不是为了让鼠标移进去 |
| 鼠标可进入 | 否，`pointer-events: none` | 悬浮层里没有任何可交互或可选中的内容，必须让点击穿透到下层列表 |
| 位置 | 覆盖在书签列表上方，靠近触发行 | 见下方技术限制 |
| 边界处理 | 靠近底部时向上翻转 | |
| 键盘可达 | 焦点在书签行上时按一个键唤出，Esc 关闭 | 无障碍要求。注意：这是纯视觉内容，屏幕阅读器用户从中得不到信息，悬浮层应标记 `aria-hidden`，键盘唤出只服务于低视力但用眼的用户 |
| 减少动态效果 | `prefers-reduced-motion` 下取消淡入位移 | 与现有动效规范一致 |

**技术限制：悬浮层不能溢出侧边栏。** Chrome 侧边栏是独立的浏览器上下文，DOM 无法绘制到网页区域。悬浮层只能在侧边栏自己的宽度内浮起，覆盖在列表上方。侧边栏宽度用户可调，实现时按可用宽度自适应，最小 300px 时快照仍要能看清。

**静默刷新（可选增强）**

hover 时后台静默发一次轻量请求核对页面状态码，检测到失效时写入链接健康数据。**注意：新方案下悬浮层里没有文字，所以这个结果不在悬浮层上呈现**，只落库供 F9 和书签行上的失效标记使用。

这一步有一个很划算的副作用：**悬浮预览是死链检测的天然载体**。用户日常浏览时顺手就积累了链接健康数据，F9 的全量检测可以只跑那些从没被 hover 过的书签。

**验收标准**

- 快速划过 20 行书签不触发任何悬浮层。**反向用例同样要过：缓慢停留在一行上必须触发**，用以捕捉意图检测写反的情况。
- 停留 400ms 后，有快照的书签弹出悬浮层，内容为一张 16:10 的页面快照。
- **悬浮层内除快照外没有任何元素。** 抽查若干条记录，不存在站点标识、站点名、标题、摘要、标签、路径、时间角标或任何文字。
- **悬浮层内只可能是页面快照。** 不存在把 `og:image` 或分类封面显示在悬浮层里的情况。
- 没有快照时**完全不渲染悬浮层**：无空卡、无占位框、无加载态、无「暂无预览」文案。
- 在一份从未打开过任何页面的存量书签库上（模拟刚安装的用户）：hover 任意书签均无悬浮层出现，且列表交互不受任何影响。
- 分别从 Aarre、地址栏和普通链接打开缺图书签，都必须等页面完整加载稳定再截图；补旧图成功时页面底部出现“封面截图已更新”，回到侧边栏后下一次 hover 出现快照。
- Chrome 星标和 Aarre 新收藏的首次截图静默完成；已有截图未满 7 天时不重拍，满 7 天后正常浏览只静默刷新一次。
- 悬浮层显示期间点击其覆盖区域，事件穿透到下层书签行并正常生效。
- 不采集清单内的域名和无痕窗口不产生快照。
- 悬浮层完全在侧边栏可视区内，靠近底部时向上翻转，不被裁切。
- 侧边栏宽度调到最小时快照仍能看清。
- 悬浮层出现时不发起任何会阻塞渲染的网络请求（静默刷新必须是异步的）。

**技术备注**

IndexedDB 从 v3 升到 v4，新增 `pageSnapshots` store，keyPath 为 `canonicalUrl`，索引 `by-captured-at` 用于过期标记和容量清理。**注意 store 名字不是 `snapshots`**——F2 的撤销快照用的是 `undoSnapshots`，两者含义完全不同。

采集走 `chrome.tabs.captureVisibleTab`，它只能截当前可见标签页。新收藏和所有正常打开方式命中的已收藏页面都由统一协调器登记目标 tab、canonical URL、资源键和 document/navigation 身份；临时目标写入 `chrome.storage.session`，AI 与截图任务写入 `chrome.storage.local`，防止 MV3 Service Worker 暂停后丢失。收到 `status === "complete"` 后仍**不能立刻截图**：先等待字体、首屏可见图片和 DOM 900ms 安静（最长 4 秒），再核对标签仍在前台、窗口聚焦、URL/文档未变化、收藏绑定仍存在。标签切走、窗口失焦、重新导航或关闭会放弃本次执行并保留持久任务，供下次正常打开时继续。已有截图还要通过 7 天新鲜度判断。

无痕窗口的判断用 `tab.incognito`，不要靠 `chrome.extension.inIncognitoContext`（Service Worker 里拿不到正确值）。

截图返回的是 PNG data URL，要在 Service Worker 里用 `OffscreenCanvas` 加 `createImageBitmap` 转成 WebP 并裁到 16:10，不要把原始 PNG 存进 IndexedDB——单张能有几 MB。

容量上限设 2,000 张，超出时按 `by-captured-at` 淘汰最旧的。

## 5. 封面策略 v2

这一章是 F3 的完整规格。目标是：**每一条书签在 48px 列表里都有一个清晰、精致、可辨识的标识，且用户能一眼看出它是哪个站点。**

注意这个目标的措辞。它不是「每条书签都有一张封面图」——那个目标现在也能达到，只是达到的方式（糊 favicon 加品牌图兜底）让用户什么都感知不到。真正要解决的是**辨识度**，不是覆盖率。

### 5.1 现状与失败原因

现有实现（`src/lib/page-essence.ts` 的 `representativeImage()`，`src/lib/thumbnail.ts` 的 `cacheRepresentativeImage()`）已经做了社交元数据、`image_src`、JSON-LD、正文主图四级候选，GitHub 仓库还有专门的 OpenGraph 分支。这个基础是对的，但它有五个结构性缺口：

1. **优先级搞反了。** 现在是页面封面优先、favicon 兜底。但 48px 只有 2,304 个像素，页面封面里的文字和细节完全不可读，反而是 favicon 代表的品牌标识更容易辨认——只是它太小太糊。正确的做法是拿高清的品牌标识做首选，而不是把页面封面缩到看不清。
2. **完全没用 `apple-touch-icon` 和 Web App Manifest。** 这是最大的一处浪费，也是上一条能不能修好的关键。几乎所有正经站点都提供 180×180 的 `apple-touch-icon`，很多 PWA 站点的 manifest 里还有 512×512 图标。这两个来源清晰度远超 favicon，不需要登录、不需要额外授权，代码里目前一行都没用。
3. **兜底方案的位置摆错了。** 现在的兜底是 Chrome 的 32px favicon，再失败就是 Aarre 自己的品牌图标。兜底被当成「最后没办法的时候凑合一下」，所以质量最差。而随着分类封面资产就位（见 5.3），兜底反而是质量最有保证的一层——它必须变成**质量下限**而不是**最后手段**。
4. **没有质量校验。** 下载到 1×1 追踪像素、纯色占位图、极端长条横幅时，一样会被裁成方图存下来。
5. **没有通用横幅识别。** 很多站点所有页面共用同一张 `og:image`（典型如文档站、SaaS 后台）。现在会把这张图重复下载几十次，并且让整个文件夹里的书签长得完全一样——这是当前最难看的失败模式。

### 5.2 核心设计：两条并行管线，而不是一条级联

**第一个关键判断：48×48 的方格里，品牌标识永远打败页面内容。**

48px 只有 2,304 个像素，Retina 下也只有 96px。在这个尺寸下：

- **网页截图完全不可读**，缩下来就是一片灰噪，用户什么都感知不到。
- **文字型社交卡不可读**。GitHub 的 OG 卡片、大多数博客的 OG 图，主体是文字排版，缩到 48px 后只剩色块。
- **品牌标识高度可读**。用户对熟悉站点的 logo 有肌肉记忆，一眼就能扫到。
- **单一主体的照片勉强可读**。视频缩略图、商品图这类有明确主体的还能看出个大概。

正确的参照系是 **iOS 的 App 图标网格**，不是文章卡片流。App 图标之所以在小尺寸下既好看又好认，靠的是三件事：每一个都是品牌标识而不是内容缩略图；有统一的圆角方形画布和留白；品牌色本身提供了区分度。

所以列表缩略图的默认答案是站点标识，页面封面只在大尺寸下才有价值。

**第二个关键判断：两种资产走两条独立管线，各自服务不同尺寸。**

| 管线 | 用在哪 | 优先级 |
| --- | --- | --- |
| **管线 A · 站点标识** | 48px 书签列表（默认）、搜索结果、整理提案的行内标识 | `apple-touch-icon` → manifest icons → 高分辨率不透明图标 → **分类封面兜底** |
| **管线 B · 页面封面** | 整理提案预览、周报等非收藏库瀑布流场景 | 规则表结构化端点 → `og:image` / `twitter:image` → 回退到分类封面；收藏库瀑布流按 2026-07-31 定稿只用真实截图或本地 Aarre 兜底 |

两条管线各自独立降级，互不阻塞。管线 A 的最后一级是本地资产，所以**列表封面 100% 有内容，永远不会出现灰色地球或空白格**。

**注意悬浮预览（F22）不属于这两条管线中的任何一条。** 它只用页面快照，封面资产一概不进预览窗——理由见 F22。页面快照因此也不再是管线 B 的候选之一，它是独立的第三类资产。

分开存还有一个巨大的副作用收益：**站点标识按域名共享缓存**。1,000 条书签可能只涉及 200 个域名，管线 A 的存储量直接降到五分之一，而且同域名的第二个书签零成本拿到图。

**规则表可以为特定站点打破默认。** 少数站点的页面封面在小尺寸下确实可读——视频站的缩略图是真实画面、电商的商品图有明确主体。规则表里可以给这些站点标注 `listUsesPageImage`，让它们的列表缩略图改用管线 B。这是例外而不是默认。

### 5.3 质量地板：兜底图是下限，不是最后手段

这一节是整个封面策略的判据来源，所有取舍都从这里推导。

正在生成的分类封面资产（约 40 个分类，风格参照 `design-assets/bookmark-covers/taxonomy-pilot/`）有非常明确的规格：`1254 × 1254` 原生、sRGB 不透明 PNG、**每张只含三个精确颜色**（近黑 `#141413`、象牙白 `#FAF9F5`、一个强调色）、粗手绘线条、单一视觉隐喻、无文字无 Logo 无渐变无阴影。

这套资产在 48px 下的表现非常好，原因不只是分辨率高，而是三件事叠加：**1254px 缩到 48px 是 26 倍下采样，绝对锐利；只有三色且高对比，缩小后形状不会糊；满版不透明背景，在列表里自成一块干净的色块。**

**由此得出一条硬规则：任何从网络抓来的真实资产，如果达不到这个水准，就不要用，直接走分类封面。**

这条规则的方向和常规做法是反的。通常兜底是「实在没办法了凑合一下」，所以质量最差，于是抓取逻辑会拼命想用上任何抓到的东西。现在兜底是**有质量保证的下限**，所以抓取逻辑可以变得非常挑剔——宁可用一张漂亮的分类封面，也不要一张糊的真实图标。

**但这条规则不能被误读成「多做几张兜底图就好了」。**

分类封面总量固定在约 40 张，一个分类一张，这是维护上限，不扩充。所以工程重心必须放在**另一个方向**：把真实资产的命中率做上去，让兜底尽可能少被触发。

这两件事的分工要说清楚：

- **质量地板**决定「什么资产不能用」。它保证下限，但它本身不提升表现力。
- **来源丰富度**决定「多少书签能用上真实的、站点专属的封面」。它才是表现力的真正来源。

如果只做前者不做后者，结果就是一半以上的书签都掉到那 40 张图上——40 张图铺 1,000 条书签，平均每张要出现 25 次，一屏里必然大量重复。这不是靠加图能解决的，加到 200 张也只是把 25 次变成 5 次，而维护成本翻五倍。

**正确的解法是把兜底率压到足够低。** 目标是不高于 12%：1,000 条书签里约 120 条走兜底，分摊到 40 个分类，平均每张封面出现 3 次左右，视觉上不构成重复。这个目标怎么达成，见 5.5 的来源清单——需要把管线 A 从现在的「一个 `og:image` 加一个 favicon」扩到七八个来源。

**具体的准入闸门（管线 A）**

| 检查项 | 阈值 | 不通过怎么办 |
| --- | --- | --- |
| 原生边长 | ≥ 128px，推荐 ≥ 180px | 走分类封面 |
| 是否需要放大填满画布 | 绝对不允许放大 | 走分类封面 |
| 背景 | 必须不透明满版 | 走分类封面 |
| 宽高比 | 偏离 1:1 不超过 20% | 走分类封面 |
| 48px 下的可辨识度 | 缩放后仍有清晰主体轮廓 | 走分类封面 |

48px 在 Retina 下是 96px，128px 只有 1.3 倍余量，勉强够用；180px 有近 2 倍余量，这才是安全线。**Chrome 的 32px `_favicon` 服务因此基本退出管线 A**——它连地板都摸不到。这是一个重要的取舍：宁可少 20% 的「真实品牌图标」，也不要任何一个糊图标。

「背景必须不透明满版」这一条正好和 Apple 的规范对齐：`apple-touch-icon` 按规范不支持透明通道，所以它天然满版不透明。这让优先级链条自然收敛到 `apple-touch-icon` 和 manifest 图标这两个来源。

**明确不做：色底合成**

不对图标做主色提取、不生成浅色底板、不把小图标叠在生成的色块上。理由：

1. 一个低分辨率图标叠在色底上，不会因为有了底就变精致，只是从「一个糊图标」变成「一个糊图标加一块色」。
2. 各站点图标的设计语言差异极大（线条粗细、配色、几何风格都不同），套上统一色底后不会变整齐，反而因为「统一的底 + 杂乱的前景」形成更强的视觉噪音。
3. 现在没必要了。分类封面已经提供了一套**成体系、同风格、质量有保证**的视觉资产，任何合成方案都不可能比它更好。

**同时废弃「主色 + 首字」生成式字标。** 那正是上面否掉的合成路线，而且分类封面在信息量和美观度上都完全覆盖了它。

### 5.4 站点规则表

新建 `src/lib/cover-registry.ts`，用声明式规则表描述高频站点的特殊策略。规则表是纯数据 + 纯函数，容易测试、容易扩充，不散落在业务逻辑里。

规则表在管线 A 里是**最高优先级**（第 0 级），因为它是唯一能人工确认「这个站点最好的资产在哪」的地方。对压低兜底率来说，它是最直接的杠杆：只要覆盖了用户最常收藏的那批站点，兜底率就会明显下降。

每条规则可以声明四件事：

- **`brandAsset`**：直接指定该域名的品牌资产地址，绕过全部自动探测（管线 A 第 0 级）。用于自动探测拿不到、或拿到的不是最好那一个的站点。
- **`pageImage`**：从 URL 直接拼出页面封面地址的函数（管线 B）。命中时完全不需要抓取页面 HTML，又快又稳。
- **`skipPageImage`**：明确标记这个站点的 `og:image` 没有价值（登录墙、通用横幅），管线 B 直接放弃。
- **`listUsesPageImage`**：例外标记。默认列表用管线 A 的站点标识，只有标了这一项的站点才在 48px 列表里改用页面封面。仅给「页面图有明确单一主体」的站点开启。

**规则表规模建议做到 150 条以上，而不是 25 条。** 它是纯数据文件，不含图片资产，所以不受「40 张兜底图」那种维护上限的约束——加一条规则的成本是一行配置，不是一张要长期维护的图。收藏行为高度集中在头部站点，覆盖 150 个域名大概能覆盖真实书签库的一半以上，性价比远高于优化自动探测的边缘情况。

规则可以半自动生成：跑一遍自动探测，把「探测失败」和「探测到的资产小于 180px」的域名按出现频次排序，人工逐个补 `brandAsset`。这样工作量集中在真正有收益的地方。

**下表是初始的一批，覆盖策略示例：**

| 站点 | 管线 A（列表标识） | 管线 B（大图预览） |
| --- | --- | --- |
| `github.com/{owner}/{repo}` | GitHub 品牌标识 | `opengraph.githubassets.com/1/{owner}/{repo}`（现有逻辑迁移） |
| `youtube.com/watch?v={id}`、`youtu.be/{id}` | **例外，列表用页面图**（视频缩略图有明确主体） | `i.ytimg.com/vi/{id}/maxresdefault.jpg`，404 降 `hqdefault.jpg` |
| `bilibili.com/video/{bvid}` | **例外，列表用页面图** | `og:image`，B 站是真实封面 |
| `xiaohongshu.com` | 品牌标识 | `skipPageImage`（登录墙） |
| `x.com`、`twitter.com` | 品牌标识 | `skipPageImage`（登录墙） |
| `zhihu.com/question/*` | 品牌标识 | `skipPageImage`（通用横幅） |
| `zhuanlan.zhihu.com`、`mp.weixin.qq.com` | 品牌标识 | `og:image`，文章有真实配图 |
| `juejin.cn`、`segmentfault.com` | 品牌标识 | `og:image` |
| `npmjs.com/package/{name}` | 品牌标识 | `skipPageImage` |

### 5.5 管线 A · 站点标识

这一节是把兜底率从「一半以上」压到 12% 以下的全部工作。

现有实现只有两个来源：`og:image` 和 Chrome 的 32px favicon。前者不适合 48px，后者过不了质量地板。所以现在的真实有效来源接近于零——这才是封面表现力差的根本原因，不是兜底图不够多。

**候选顺序（按域名抓取一次，全站共享）**

| 顺序 | 来源 | 典型尺寸 | 说明 |
| --- | --- | --- | --- |
| 0 | **规则表指定的资产地址** | — | 人工确认过的最佳来源，优先级最高。见 5.4 |
| 1 | `<link rel="apple-touch-icon">` 及 `-precomposed` | 180×180 | 取声明尺寸最大的。按 Apple 规范不支持透明通道，天然满版不透明 |
| 2 | **约定路径直接探测** | 152–180 | 见下方说明，这是一处被普遍忽略的免费覆盖率 |
| 3 | Web App Manifest 的 `icons` | 192 / 512 | PWA 站点常有 512×512 |
| 4 | **SVG 图标栅格化** | 任意 | 见下方说明，质量最高的一类来源 |
| 5 | `<link rel="icon">` 中声明尺寸 ≥ 128px 的位图 | 128–256 | 很多站点提供 192×192 PNG |
| 6 | **`msapplication-TileImage`** | 144 / 270 | Windows 磁贴图标，同样被普遍忽略 |
| 7 | 分类封面兜底 | 384 | 永远成功 |

每个候选都要过 5.3 的准入闸门，任何一项不通过就继续往下走。**唯一的加工是裁成正方形并统一圆角**，不做色底合成、不做主色提取、不做放大。

**第 2 级 · 约定路径探测**

Apple 的规范明确写了：如果页面没有声明 `<link rel="apple-touch-icon">`，浏览器会去站点根路径找约定文件名。所以**大量站点有这个文件但没有在 HTML 里声明它**，只解析 HTML 会白白漏掉。

按顺序探测：`/apple-touch-icon-180x180.png` → `/apple-touch-icon.png` → `/apple-touch-icon-precomposed.png` → `/apple-touch-icon-152x152.png`。用 HEAD 请求先判存在，命中即停。四个请求的成本很低，而且按域名只做一次。

**第 4 级 · SVG 图标栅格化**

`<link rel="icon" type="image/svg+xml">` 和约定路径 `/favicon.svg` 现在相当普及。SVG **与分辨率无关**，栅格化到 192px 永远锐利——这类来源的质量上限比任何位图都高，却完全没被利用。

在 `OffscreenCanvas` 里渲染，注意两点：只接受不含外部引用和脚本的静态 SVG；渲染有超时上限，防止恶意 SVG 拖住流程。

**关于透明背景：允许，但合成到卡片自身的表面色**

前一版规定「背景必须不透明满版」，这会挡掉大量 SVG 和 `rel=icon` 资产，和压低兜底率的目标直接冲突。调整为：

允许透明背景，渲染时合成到**卡片自身的表面色**（浅色模式纯白、深色模式对应的表面色）。这和 5.3 否掉的做法有本质区别——**不发明任何新颜色，也不为图标额外造一个色块**，只是把图标放在它本来所在的卡片底色上，视觉效果等同于一个白底图标。

同时加一道墨迹闸门，防止出现「一个几乎空白的方格」：图标本体的不透明像素占画布面积低于 15%，或与表面色的对比度不足时，判定为过于单薄，走分类封面。

**同品牌多域名归并**

`docs.github.com`、`gist.github.com`、`github.com` 用的是同一套品牌资产。先按完整 host 抓取，失败时回退到注册域（eTLD+1）再试一次。这同时提高命中率和减少请求量。

**已从候选中移除的来源**

- `og:logo` 和 JSON-LD 的 `Organization.logo`：通常是横向品牌字标，宽高比远离 1:1，裁方图后残缺。
- Chrome 的 `_favicon` 服务：32px，达不到清晰度地板。
- **第三方图标服务**（Google S2 favicons、DuckDuckGo icons、unavatar 等）：它们确实能提供更高分辨率，但会把用户的完整书签域名列表逐个发给第三方。这和排除第三方截图服务是同一条理由，不能因为「只是图标」就放松。

**分类封面兜底**

前七级都不达标时，按记录的 `topics` 字段映射到分类封面。映射基于 `topics` 的语义，不是文件夹名——真实用户的文件夹结构不可预测。

`topics` 也为空时（还没被 AI 处理过的记录），使用一张通用的「未分类」封面，并在该记录被 AI 处理后自动替换。

**总量固定在约 40 张，一个分类一张，不做变体扩充。** 这是明确的维护上限。视觉重复靠压低兜底率解决，不靠加图。

不过有一个零维护成本的补充手段值得做：**按 `hash(域名)` 对底色做 ±6% 以内的确定性明度偏移**。同一分类的多条书签仍然是同一个色系（分类识别不受影响），但连续出现时不会完全一样。这不引入新资产、不引入新颜色，只是同一强调色的明度变体。确定性很重要——同一个域名永远得到同一个明度，用户会形成视觉记忆。

这一条能缓解当前试制版的一个现象：旅行类六个变体共用同一个 `#6A9BCC`，连续出现多条时视觉上连成一片蓝，预览截图里已经能看到。

**关于内置第三方 Logo 的建议**

需求里提到「从网上找一个小红书的高清 logo 打包进来」。不建议这样做，有三个原因：

1. 把第三方商标图片打包进扩展分发有商标风险，Chrome Web Store 审核也可能提出异议。
2. 需要长期维护一堆图片资产，站点改版就要跟着更新。
3. **完全没有必要。** 小红书、X、知乎这类站点的 `apple-touch-icon` 都是公开可取的，不需要登录——它们本来就是给浏览器用的。管线 A 会自动拿到，而且永远是站点当前的最新版本。

对于极个别连 `apple-touch-icon` 都拿不到的站点，用分类封面兜底而不是 logo 本体：视觉上比拼凑的 logo 更精致，且零商标风险、零维护成本。

### 5.6 管线 B · 页面封面

只服务于 160px 以上且允许宣传图的场景：整理提案预览、周报等。**不进 48px 列表、不进悬浮预览，也不进网页端收藏库瀑布流。**

候选顺序：

1. **规则表的结构化端点。** 见 5.4。由 URL 直接拼出地址，不抓页面 HTML。
2. **页面社交封面。** 保留现有的 `og:image` / `twitter:image` / `image_src` / JSON-LD / 正文主图四级提取，增加下面两道闸门。
3. **分类封面。** 与管线 A 共用同一套资产，放大到 384px 使用。

两级真实来源在全目录扫描时就能拿到，不依赖用户打开过页面，所以存量书签一样覆盖。

**质量校验（下载后、裁切前）**

拒绝并放弃管线 B 的情况：

- 任一边小于 200 像素（在卡片视图里放大会糊）。
- 宽高比超过 4:1 或小于 1:4（横幅条，裁切后没有内容）。
- 单一颜色占比超过 95%（纯色占位图或空白图）。
- 文件小于 1KB（追踪像素）。

**通用横幅检测**

这一条能解决最难看的失败模式。扫描过程中维护「域名 → 图片地址 → 出现次数」的计数，同一域名下三个以上不同页面拿到同一张图时，判定为站点通用横幅：

1. 该域名后续页面不再重复下载这张图。
2. 已经用它做页面封面的记录清空管线 B，改用分类封面。
3. 该域名自动补一条 `skipPageImage` 的运行时规则，写入 `siteBrands`。

因为列表默认已经用管线 A 的站点标识，通用横幅不会再造成「一屏书签长得一模一样」——但它仍然会让卡片视图和周报里出现整片相同的图，而且会白白重复下载几十次，所以这个检测依然要做。

### 5.7 存储与显示规格

| 资产 | 尺寸 | 格式 | 存储位置 |
| --- | --- | --- | --- |
| 站点标识（管线 A） | 192×192 | WebP q0.85 | 新建 `siteBrands` store，按域名共享 |
| 分类封面 | 384×384 | WebP q0.85 | 随扩展打包，`src/assets/covers/` |
| 页面封面（管线 B） | 长边 512，保留原始宽高比 | WebP q0.80 | `resources` store，随记录 |
| 页面快照（F22） | 长边 960，16:10 | WebP q0.75 | 新建 `pageSnapshots` store，按 canonicalUrl；满足 240–300px 瀑布流卡片的 Retina 显示 |

站点标识从 128 提到 192，是为了和分类封面的清晰度对齐——列表用 48px、卡片视图和整理提案里最大用到 96px，192 都有余量。（悬浮预览不再显示站点标识，见 F22 的 2026-07-30 修订。）

**分类封面的打包规格。** 原始资产是 `1254 × 1254` PNG，不打包进 `dist/`。打包 `384 × 384` WebP，每张约 10–20KB，约 40 张合计不到 1MB。列表 48px 和卡片视图都够用。原始资产留在 `design-assets/`。

页面封面不裁方图。卡片视图和周报是横向布局，保留原始比例信息量更大；需要方图时在显示层裁。

页面快照单独建 store，不放在 `resources` 里。两个原因：它按 `canonicalUrl` 而不是书签 ID 索引（同一 URL 被收藏两次共享一张快照）；它是唯一**不参与云端同步**的资产（见 F14），单独存放能让同步逻辑天然不碰它。

按 1,000 条书签估算：60% 有页面封面约 21MB，200 个域名的站点标识约 2MB，快照按活跃使用后 40% 覆盖、每张约 45KB 计约 18MB。合计 40MB 出头，`unlimitedStorage` 完全承受得住。

**显示层：**

| 场景 | 用什么 |
| --- | --- |
| 48px 书签列表 | 管线 A（规则表标了 `listUsesPageImage` 的站点除外） |
| 搜索结果、整理提案行内 | 管线 A |
| 网页端收藏库瀑布流 | 真实页面截图；为空时用 40 张本地 Aarre 兜底图，不读管线 B |
| 其他卡片视图、周报 | 管线 B，为空时用分类封面（384px 原生，放大不糊） |
| 悬浮预览（F22） | **只用页面快照**，没有就整个悬浮层不渲染 |

最后一行是刻意的：封面资产不进悬浮层，悬浮层只放真实快照。理由见 F22。

设置页提供「列表封面风格」开关，可选「站点标识（整齐）」和「页面封面（丰富）」。**默认站点标识**——这是 48px 下唯一能让用户真正感知到内容的选项。

### 5.8 数据结构变更

`ResourceRecord` 新增字段（全部可选，`normalizeResourceRecord` 需要兼容旧记录）：

```
coverSource?: string        // 诊断用，如 "snapshot" / "registry:youtube" / "og:image"
coverUpdatedAt?: string
categoryCoverId?: string    // 兜底封面 ID，如 "travel-places/signpost"，仅字符串
snapshotAt?: string         // 页面快照采集时间，仅用于容量清理时按时间淘汰，不呈现给用户（见 F22 修订）
```

`siteBrands` store 的记录结构：

```
host: string                // 主键
iconDataUrl?: string        // 192×192 WebP，仅在通过准入闸门时存在
iconSource?: string         // "apple-touch-icon" / "manifest" / "icon"
iconRejectReason?: string   // 未通过闸门的原因，诊断用，如 "below-128px" / "transparent-bg"
skipPageImage?: boolean     // 运行时由横幅检测写入
updatedAt: string
```

`iconDataUrl` 为空表示该域名的标识没能通过闸门，显示层直接走分类封面。**记录 `iconRejectReason` 很重要**：它是唯一能回答「为什么这个站点没用上真实图标」的数据，也是后续调整阈值的依据。

保留现有的 `thumbnailDataUrl` 和 `imageUrl` 字段名承载管线 B，避免破坏已有数据和云端映射。原来只在 GitHub 上生效的 `needsRepresentativeImageRefresh()` 用 `coverSource` 的优先级比较替代。

IndexedDB 从 v2 升到 v3（v2 由 F2 的 `undoSnapshots` 占用），新增 `siteBrands` store，keyPath 为 `host`。

### 5.9 验收标准

在一份不少于 300 条的真实书签样本上（必须包含中英文站点、文档站、视频站、社交站、内网地址）：

**管线 A · 列表标识（这是用户每天看到的）**

这一组指标里有两条是互相拉扯的硬指标，必须同时满足，任何一条不达标都算失败：

- **零上采样。** 抽查全部记录，不存在任何原生尺寸小于 128px 的图标被显示出来。这是质量地板的检验。
- **分类封面兜底不高于 12%。** 这是来源丰富度的检验。兜底图总量固定在 40 张，兜底率一旦超过 12%，单张封面的平均出现次数就会突破 3 次，一屏内开始出现可感知的重复。

同时满足这两条，意味着不能靠「放松质量换覆盖」也不能靠「加图掩盖不足」，只能把 5.5 的来源清单真正做全。这是本章的核心工程目标。

其余指标：

- 覆盖率 100%，不出现灰色地球、破图占位或空白方块。
- 来自 `apple-touch-icon`（含约定路径探测）或 manifest 的不低于 65%。
- 来自 SVG 栅格化的不低于 8%（检验这条新增来源真的接上了）。
- 透明背景资产合成到表面色后，不出现墨迹稀薄的空白方格（墨迹闸门生效）。
- 混排视觉检查：真实品牌图标和分类封面交替出现时，圆角、留白、尺寸完全一致，不出现某几行明显「脏」的情况。
- 连续 5 条以上同分类兜底书签时，底色不连成一片（检验明度偏移生效）。
- 抽查 `iconRejectReason` 分布，确认拒绝原因集中在「确实无可用资产」而不是闸门过严。

**管线 B · 卡片与周报用的页面封面**

- 全目录扫描后（不依赖用户打开过页面），有页面封面的比例不低于 45%。
- 为空时卡片视图正常回退到分类封面，不出现破图或空白区。

**性能与隐私**

- 全量扫描 300 条的封面处理总耗时不超过 AI 处理耗时的 30%（封面不能成为扫描瓶颈）。
- 同一域名的站点标识只抓取一次，可通过请求日志验证。
- 内网和敏感地址不发起任何图片请求。

### 5.10 明确排除的方案

**色底合成与生成式字标**：不做主色提取、不生成浅色底板、不把图标叠在生成色块上、不做「主色 + 首字」字标。一个低分辨率图标加一块色底不会变精致，各站点图标风格差异极大，统一底 + 杂乱前景反而是更强的视觉噪音。分类封面已经提供了成体系、同风格、质量有保证的资产，任何合成方案都不可能更好。详见 5.3。

**上采样**：任何需要放大才能填满画布的资产一律拒绝。48px 在 Retina 下是 96px，128px 是勉强下限，180px 才是安全线。Chrome 的 32px `_favicon` 服务因此退出管线 A。

**网页截图作为列表缩略图**：48px 下完全不可读，用户感知不到任何内容。截图只用于管线 B 的大图预览。

**第三方截图服务**（microlink、urlbox、screenshotone 等）：会把用户的完整书签 URL 列表发给第三方，和产品的隐私定位直接冲突，且有持续成本和速率限制。不采用。

**后台批量开标签页截图**：技术上直接堵死，不只是「不划算」。`captureVisibleTab` 的名字就说明了它只能截取当前**可见**的标签页，后台标签页截不到。要批量截图必须把每个页面轮流切到前台，用户会看到页面疯狂闪烁。绕过这一点只有 `chrome.debugger` + `Page.captureScreenshot`，但那会在页面顶部显示「正在调试此浏览器」的黄条，且 `debugger` 权限在 Chrome Web Store 审核中极为敏感。详见 F22。

这一排除项不包含上文的「用户主动前台逐页补拍」：后者只复用一个专用活动标签页，行为和限制在启动前完整告知，失焦即停，也不申请 `debugger` 权限。

**Chrome 内部 PageImageService**：Chrome 新版侧栏用的就是它，但那是内部 Mojo 接口，扩展调不到。已经确认过，不再重复评估。

## 6. M2 · 立差异

### F7 · 主动整理提案

**要解决什么问题**

现在的 Agent 是被动的：用户想不到要问，它就永远不说话。但书签库最痛的问题——乱、重复、失效、堆积——用户其实**说不出口**，因为他自己也不知道乱在哪。

这是整个产品最重要的一个功能。它同时具备技术壁垒（执行能力已经写完了）、情感冲击（解决了用户描述不清的痛）、以及竞品结构性做不到的特性（平行库产品没有原生书签的写权限）。

**怎么做**

全目录扫描完成后，自动生成一份整理提案，包含四类发现：

| 类型 | 判定依据 | 数据来源 |
| --- | --- | --- |
| 可归类 | 同一 `topics` 下散落在多个文件夹的书签 | AI 已生成的 `topics` 字段 |
| 重复 | 同一资源键对应多个 bookmark ID | `nativeBookmarkIds.length > 1`，几乎零成本 |
| 失效 | F9 死链检测的结果 | HTTP 状态码，不是 AI 猜测 |
| 过大 | 单个文件夹超过阈值（建议 150 条） | 书签树统计 |

**呈现方式：** 在 F5 选定的全页 UI 里，分组展示、逐条勾选、实时预览「整理后的文件夹结构长什么样」。顶部一个「全选并应用」，底部一个「一键撤销」（依赖 F2）。

**边界要守死：**

- 失效判定必须基于真实的 HTTP 检测，不允许凭标题或 AI 摘要猜测。这条规则现在已经写在 prompt 里了，实现时不能放松。
- 重复合并默认只保留最早创建的那个，且要在预览里明确显示将删掉哪些。
- 任何删除类提案默认**不勾选**，需要用户主动勾。

**验收标准**

- 在 300 条真实书签上运行，提案中的「可归类」建议经人工判断有 70% 以上是合理的。
- 应用一批提案后点撤销，书签树完整回到应用前的状态。
- 提案生成过程最多调用一次 AI（用已有的 `topics` 做本地聚类，只在生成叙述性说明时调 AI）。

### F8 · 两段式检索

**要解决什么问题**

两个问题共用一个解法。

第一，`askBookmarkAgent` 把全目录压成紧凑索引一次性塞进 prompt，上限 110,000 字符。现在 269 条刚好塞得下，但重度用户有两三千条，到那时会同时触发截断导致答案不完整、token 成本线性上涨、响应变慢。这不是检索，是暴力填充。

第二，`searchLocalResources` 只做 substring 匹配加权打分，中文不分词、无同义词。搜「机器学习」找不到 AI 标了「ML」「深度学习」的条目——而 AI 打的标签恰恰大量是这种同义概念。

**怎么做**

**第一段 · 本地召回**，取 Top 30–50 条。**第二段 · 模型精读**，只把这几十条的完整信息交给模型，而不是全目录的压缩摘要。上下文小了一个数量级，每条能给的信息反而更丰富，答案质量会更好。

关键在第一段的召回怎么做。这里有一条硬约束：**用户永远不应该看到「embedding」这个词，更不应该需要去配置它。** 中国用户配 DeepSeek 的很多，而 DeepSeek 没有 embedding 模型；让用户为了搜索功能再去申请另一家的 Key，是产品设计的失败。

所以召回能力分三层，**全部自动判定，逐层自动降级，用户无感**：

**第一层 · 强词法召回（默认，覆盖 100% 用户，零配置零成本）**

这一层是主线，不是兜底。三个组成部分：

- **中文二元组切分。** 现有的 `searchLocalResources` 只做 substring 匹配，中文完全不分词。改成二元组后「机器学习」能匹配到包含「学习机器」以外的各种组合形态。
- **拼音首字母匹配。** 输入 `jqxx` 匹配「机器学习」。这是中文用户的高频习惯，成本极低，但体感提升非常明显。
- **AI 生成的检索别名（这一条是关键）。** 现有的 enrichment prompt 已经在返回 `summary` / `tags` / `topics`，**再加一个 `aliases` 字段几乎零成本**——同一次调用，多几十个 token。让 AI 输出这条书签的同义检索词，包括中英对照和常见缩写。

  举例：一篇讲 Machine Learning 的文章，除了 `tags: ["机器学习","监督学习"]`，再输出 `aliases: ["machine learning","ML","人工智能","AI","模型训练"]`。用户搜其中任何一个都能命中。

  **这是用已有的 AI 调用免费换来的语义能力**，不需要向量、不需要额外服务、不受服务商限制。对绝大多数「我记得收藏过讲 X 的东西」这类查询，它的效果和 embedding 相差不大。

**第二层 · 本地 embedding（可选增强，仍然零配置）**

用 `transformers.js` 加载一个小型多语言模型（如 int8 量化后约 30–50MB 的多语言 e5 或 bge 系列），完全在本地推理。这条路对「完全没有词汇重叠的描述性长查询」效果明显更好。

三个实现要点：

- **模型不打包进扩展**，首次启用时按需下载并缓存。扩展包体积不能因此膨胀几十 MB。
- **需要考虑国内可访问性。** HuggingFace CDN 在国内访问不稳定，需要准备可访问的镜像或自托管。这一点要在实现前先验证，不能想当然。
- **批量向量化不能在 Service Worker 里跑。** MV3 的 Service Worker 会被 Chrome 在空闲后终止，长时间的推理任务要用 Offscreen Document API。

做成设置项，文案写成「启用更聪明的搜索（首次需下载约 40MB 语言包）」，**不出现 embedding、向量、模型这些词**。

**第三层 · 服务商 embedding（自动判定，完全隐形）**

用户的服务商本来就支持 embedding 时（OpenAI、Gemini），自动使用，价格极低——1,000 条书签一次性向量化的成本可以忽略。DeepSeek 用户自动跳过，界面上不出现任何相关提示，也不会因此报错或降级提醒。

服务商能力用一张内置的能力表判定，不要在运行时试探性发请求。这张表要标注核对日期，实现前重新核实各家最新情况。

**三层的关系**

第一层永远启用。第二、三层可用时，把它们的召回结果与第一层取并集后重排。**任何一层不可用都不影响功能可用性，只影响召回质量。** 第一层单独工作时的效果必须达到「日常够用」，这是验收的硬指标。

向量全部缓存在本地 IndexedDB，不上云。这意味着**语义搜索不再需要登录和云端**，现有的 pgvector 方案可以整个下线。这不是砍掉云端的理由，而是让云端职责变干净的理由——见 F14。

**存量书签的别名补齐**

`aliases` 是新增字段，已扫描过的书签没有。需要一个轻量批处理：只发送标题、URL、已有标签给 AI，不发正文，单条成本极低。作为全目录扫描的一个可选子任务，或者在空闲时后台渐进补齐。

**验收标准**

- 2,000 条书签下，Agent 单次提问的 prompt 长度不超过 20,000 字符。
- **仅第一层启用时**（模拟 DeepSeek 用户）：搜「机器学习」能命中标题只有「Machine Learning」的条目；输入 `jqxx` 能命中「机器学习」相关条目；搜「怎么让页面加载更快」能召回标题为「Web Vitals 优化实践」的条目。
- 切换到 DeepSeek 后，设置页和搜索界面不出现任何关于 embedding 或向量的提示、警告或降级说明。
- 第二层的语言包下载失败时，搜索静默回退到第一层，不弹错误。
- 向量化或别名补齐的耗时和成本在启动前明确告知用户。

### F9 · 死链检测

**要解决什么问题**

存量书签里失效链接的比例通常在 10–20%，用户完全无感。Bookmark Sidebar 有这个功能，是它 30 万用户的重要留存点之一。Aarre 可以做得更进一步。

**怎么做**

作为全目录扫描的一个附加阶段。发 `HEAD` 请求（不支持时降级为 `GET` 但只读响应头），按域名限速，记录状态码。

分类要谨慎，不能把临时问题判成永久失效：

- `404` / `410` → 判定失效。
- `403` / `401` → 判定为需要登录，**不算失效**。
- `5xx` / 超时 → 标记为「暂时无法访问」，下次扫描重试，连续三次失败才升级为失效。
- 重定向到域名首页 → 标记为「内容可能已删除」，这是很常见的软 404。

**增值部分：** 检测到失效后，让 AI 基于已有的标题、摘要、标签推荐替代链接或 Web Archive 存档地址。这是竞品没有的一步。

**验收标准**

- 检测 300 条书签的耗时不超过 5 分钟。
- 登录墙站点（如小红书、X）不被误判为失效。
- 检测结果进入 F7 的整理提案，用户可批量处理。

### F10 · 重复书签合并

**要解决什么问题**

用户不知道自己有重复收藏。这是最容易兑现的一份惊喜。

**怎么做**

**这个功能几乎是免费的。** `importNativeBookmarks()` 已经按资源键做了分组，同一 URL 的多个书签会合并成一个 `ResourceRecord`，`nativeBookmarkIds` 数组里存着全部 bookmark ID。所以判定重复只需要一个条件：`nativeBookmarkIds.length > 1`。

只需要补 UI 和合并动作：展示重复组、显示各自所在的文件夹、默认保留最早创建的、其余进回收站。

**验收标准**

- 手动创建 3 个指向同一 URL 的书签，重复检测能识别为一组。
- URL 只有跟踪参数差异（`?utm_source=`）的书签也能被识别为重复——`canonicalizeUrl()` 已经清理跟踪参数，验证这条路径确实生效。

### F11 · 扫描并发、限速与成本透明

**要解决什么问题**

全目录扫描严格串行，每条一次 fetch 加一次 AI 调用。1,000 条书签大概要跑一两个小时。而用户在点下按钮时完全不知道这会花掉多少钱——对 BYOK 用户来说，这是最敏感的事情。

**怎么做**

**并发：** 按域名分桶后 3–5 路并发，同域名串行且间隔不低于 1 秒，避免被目标站点限流或封禁。

**成本预估：** 启动前显示「约 1,240 条 · 预计 18 分钟 · 约 ¥3.2」。估算基于待处理条数、当前服务商的单价、以及平均 prompt 长度。价格表内置但要标注更新日期，并说明是估算。

**成本记录：** 每次 AI 调用后累加实际 token 用量，扫描结束显示实际消耗。设置页保留累计统计。

**验收标准**

- 300 条书签的扫描耗时相比串行下降 60% 以上。
- 同一域名的请求间隔不小于 1 秒，可以通过日志验证。
- 预估费用与实际费用的偏差在 30% 以内。

### F12 · 保存时的文件夹建议

收藏浮层里，AI 基于页面内容和用户现有的文件夹结构，推荐「建议放进 前端 / 状态管理」，一次点击完成归档。

把整理成本摊到每次收藏，而不是攒到年底再来一次大扫除。这个功能的复用度很高——推荐逻辑和 F7 的「可归类」判定是同一套。

### F13 · 待读队列

「收藏了但从没打开过」是每个人收藏夹的真相，也是最容易引发共鸣的一屏。

用 `chrome.bookmarks` 节点上的 `dateLastUsed` 字段做一个待读视图。**注意这个字段有已知局限**：Chrome 只在通过书签 UI 打开时才更新它，用户手动输入 URL 访问不会更新。所以文案要写成「你很少通过书签打开它们」而不是断言「你从没看过」。这个措辞差别决定了用户觉得产品是敏锐还是不准。

## 7. M3 · 能上架

### F14 · 云端链路跑通

**当前状态是最危险的中间态。** Supabase 表结构、RLS、复合主键、离线 Outbox、指数退避、revision 并发校验代码全部写完了，OAuth 的 PKCE 流程和账号一致性校验也在，但**从来没有真实跑通过一次**。而 README 和界面已经在向用户承诺跨设备同步。

**方向已定：云端保留，职责收窄，并且从 Supabase 迁到自建服务器。**

保留的理由是硬的。Chrome Sync 只同步书签树本身——标题、URL、文件夹结构。Aarre 的整个增强层（标签、摘要、主题、别名、封面来源、笔记）都在本地 IndexedDB，**Chrome Sync 一个字节都不会带走**。用户换台电脑，书签在，AI 分析的成果全丢。这是产品承诺「增强层」时必须自己解决的问题，没有别的办法。

同时 F8 把语义检索完全本地化了，这不是削弱云端的理由，而是**让云端的职责变得干净**：

| 云端做什么 | 云端不做什么 |
| --- | --- |
| 增强层元数据的同步与备份 | 语义检索（已完全本地化，向量不上云） |
| 跨设备一致性与冲突解决 | AI 富化（BYOK 直连，不经过服务端） |
| 账号与数据隔离 | 存储任何二进制图像资产（见下） |

#### 关键优化：只同步派生指令，不同步派生产物

这一条决定了云端方案的成本量级，在自建服务器上比在 Supabase 上更重要——磁盘和带宽都是自己掏钱且固定容量。

**封面不需要同步。** 它是从公开 URL 派生出来的，同步 `coverSource`、原始图片地址、`categoryCoverId` 这些字符串（合计几百字节），另一台设备拿到后本地重新抓取即可，结果完全一致。

**页面快照不但不该同步，而且不应该同步。** 快照是设备本地的浏览痕迹，上传它等于把用户的浏览行为搬到服务端，和产品的隐私定位直接冲突。这也是 5.7 把快照单独建 store 的原因——同步逻辑遍历 `resources` 时天然碰不到它。

结果：每条书签的同步载荷约 1–2KB（摘要、标签、主题、别名、元数据），1,000 条约 1.5MB。一台轻量应用服务器的磁盘可以支撑数千用户。

#### 技术栈：与 NexVoice ControlPlane 同栈

已确认目标环境是腾讯云轻量应用服务器，与 NexVoice 共用同一台机器，**并且确认同栈**。NexVoice 的 `ControlPlane/apps/api` 已经是一套成熟可复用的底座：

| 项 | 选型 | 来源 |
| --- | --- | --- |
| 运行时 | Node ≥ 22，ESM（`"type": "module"`） | 与 ControlPlane 一致 |
| Web 框架 | Fastify 5 | `fastify@^5.6` |
| 数据库 | PostgreSQL 16，`pg` 连接池 | 复用 `control-db` 容器实例 |
| 配置校验 | zod 4 | 照搬 `src/config.ts` 的 schema 模式 |
| JWT / JWKS | `jose` | 已是 ControlPlane 依赖，正好用于验 Google `id_token` |
| 限流 | `@fastify/rate-limit` | 已在用 |
| 迁移 | 自研 SQL 迁移器 | 直接复用 `src/migrations.ts` 的 `applyMigrations` |
| 构建 / 测试 | `tsc` 构建、`tsx` 开发、`node --test` | 与 ControlPlane 脚本一致 |
| 容器 | 多阶段 Dockerfile（`node:22-bookworm-slim`） | 照搬 ControlPlane 的 Dockerfile |
| 反向代理 | 系统级 Caddy | 新增一个 site block |
| 错误上报 | GlitchTip（`crash.nexvoice.cc`） | 复用现有实例，新建一个 project |

**可以直接照搬的代码**（不要重新发明）：

- `ControlPlane/apps/api/src/migrations.ts` 的 `applyMigrations`：含 `schema_migrations` 表、`pg_advisory_lock` 串行化、逐文件事务。整个函数直接复制。
- `src/db.ts` 的连接池模式（改 `application_name`）。
- `src/config.ts` 的 zod 环境变量校验模式。
- `src/security.ts` 的 `tokenHash`（HMAC-SHA256 加 pepper）、`generateOpaqueToken`、`stableDigest`。
- `app.ts` 里 `requireInstallation` / `findInstallationIDByAccessToken` 的鉴权中间件形态，以及 `issueTokens` 的双 Token 签发模式。
- `authenticatedRateLimitKey` 的「有 Token 按 Token 限流、无 Token 按 IP 限流」写法。

**Token 模型完全沿用 NexVoice 的做法**，不要改成自签 JWT：随机不透明 Token，数据库只存 HMAC-SHA256 摘要（带 pepper），access 有效期 10 分钟、refresh 30 天。这套模式的好处是可即时吊销，而自签 JWT 做不到，且 NexVoice 已经验证过。

#### 部署形态：独立服务，共用 Postgres 实例

**结论：新增一个独立的 `aarre-api` 容器，监听 `127.0.0.1:8788`，但复用 `control-db` 这个 Postgres 实例里的一个独立 database。**

为什么不直接在 `control-api` 里加一段路由前缀：NexVoice 的 `control-api` 承载设备激活和 AI Gateway，内存限额只有 384M。Aarre 的同步流量一旦造成内存尖峰或崩溃重启，NexVoice 用户会连激活都做不了。爆炸半径不能这样耦合。

为什么不新起一个 Postgres 容器：`control-db` 限额 640M，再加一个实例是纯浪费，而且 GlitchTip 那套本身就吃内存。**共用实例、独立 database 和独立用户**，正好满足隔离要求又不多花内存。

具体配置：

```
数据库    在 control-db 内 CREATE DATABASE aarre_sync
用户      CREATE USER aarre WITH PASSWORD ...  仅授予 aarre_sync 的权限
容器      aarre-api，limits.memory 256M，端口 127.0.0.1:8788:8788
网络      加入 control-db 所在的 compose 网络（external），以 control-db:5432 连接
Caddy     新增 site block 反代到 127.0.0.1:8788
```

**代码归属：服务端代码放在 Aarre 仓库的 `server/` 目录**，自带 Dockerfile 和 `server/infra/compose.yml`。该 compose 把 NexVoice 的网络声明为 `external: true` 并接入，这样两个产品各自独立发布，互不牵连，但共享机器和 Postgres 实例。

实施前需要用 `docker network ls` 确认 NexVoice compose 的实际网络名（项目目录是 `infra/production`，默认网络名大概是 `production_default`，但要实测确认，不要猜）。

**内存预算必须先核对。** 现有占用：`control-db` 640M + `control-api` 384M + GlitchTip 整套（Django 加自己的 Postgres 和 Redis，通常 1.5GB 以上）。再加 256M 之前，先在机器上跑一次 `free -h` 和 `docker stats` 确认余量。**如果余量不足，退化方案是在 `control-api` 里加 `/aarre/v1/*` 路由前缀**，接受爆炸半径耦合，并把 `control-api` 的内存限额提到 512M。这个退化决定必须先报给产品负责人，不要自行选择。

#### 认证流程

Supabase 的 OAuth 流程不能直接搬。采用**授权码 + PKCE，在服务端交换**，`client_secret` 永不进入扩展：

1. 扩展生成 `code_verifier` 和 `code_challenge`（S256），调用 `chrome.identity.launchWebAuthFlow`，指向 Google 的授权端点，`response_type=code`，`redirect_uri` 为 `chrome.identity.getRedirectURL("auth")`（形如 `https://<extension-id>.chromiumapp.org/auth`），`scope=openid email profile`，`prompt=select_account`。
2. 拿到回调里的 `code`，POST `{ code, codeVerifier }` 到 `/v1/auth/google`。
3. 服务端用 `client_id` + `client_secret` + `code_verifier` + 同一个 `redirect_uri` 向 Google 的 token 端点交换，拿到 `id_token`。
4. **服务端用 `jose` 的 `createRemoteJWKSet` 从 Google 的 JWKS 验签**，并校验 `iss`、`aud`（必须等于自己的 `client_id`）、`exp`。
5. 从 `id_token` 取 `sub` 和 `email`，upsert 到 `users` 表（`google_sub` 唯一），按 NexVoice 的 `issueTokens` 模式签发自己的 access / refresh Token。
6. 扩展把两个 Token 存 `chrome.storage.local`，401 时用 refresh 续期。

**`redirect_uri` 需要在 Google Cloud Console 里注册为 Web 应用的重定向 URI，而这依赖正式的 Extension ID**——所以这一步和 F16 的「申请正式 Extension ID」是有依赖关系的，要排在它之后。

**`id_token` 必须在服务端验签，不能只解码不验证。** 这是这类实现最常见的严重漏洞：只 base64 解码就信任内容，等于任何人构造一个 JSON 就能冒充任意用户。

现有 `src/lib/auth.ts` 里「产品账号必须等于当前 Chrome profile 账号」的校验要保留，它是个好设计，能防止用户在共用电脑上误登他人账号。

#### 数据库 schema

两张表就够。迁移文件命名沿用 ControlPlane 风格（`001_initial.sql` 递增）。

```sql
CREATE TABLE users (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  google_sub    text NOT NULL UNIQUE,
  email         text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  last_seen_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE auth_tokens (
  id          bigserial PRIMARY KEY,
  user_id     uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_type  text NOT NULL CHECK (token_type IN ('access', 'refresh')),
  token_hash  text NOT NULL UNIQUE,
  expires_at  timestamptz NOT NULL,
  consumed_at timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX auth_tokens_user_idx ON auth_tokens (user_id) WHERE consumed_at IS NULL;

CREATE TABLE resources (
  user_id       uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  resource_key  text NOT NULL,              -- canonical URL 的 SHA-256
  revision      bigint NOT NULL DEFAULT 1,
  payload       jsonb NOT NULL,             -- 见下方载荷白名单
  note_versions jsonb,                      -- 冲突时保留的多份笔记
  deleted_at    timestamptz,                -- 墓碑，不做物理删除
  updated_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, resource_key)
);
CREATE INDEX resources_cursor_idx ON resources (user_id, updated_at, resource_key);
```

索引带上 `resource_key` 是为了让下面的复合游标能走索引，不是可选的。

**`payload` 必须是白名单字段，不是整条 `ResourceRecord` 原样上传。** 允许的字段只有：`title`、`url`、`canonicalUrl`、`folderPath`、`summary`、`tags`、`topics`、`aliases`、`note`、`coverSource`、`imageUrl`、`categoryCoverId`、`savedAt`、`updatedAt`。

**明确禁止出现在 `payload` 里的字段**（服务端要主动剥离并在收到时记一条警告，不能只靠客户端自律）：`thumbnailDataUrl`、`snapshotDataUrl`、任何 base64 图像、任何向量、任何页面正文。这是「只同步派生指令，不同步派生产物」这条原则在服务端的强制点——**光靠客户端不发是不够的，因为一次客户端 bug 就会把几十 MB 的位图写进库**。

写一个服务端测试：构造一个带 `thumbnailDataUrl` 的请求，断言入库后的 `payload` 里没有这个键，且单条 `payload` 大小上限（建议 32KB）被强制。

**墓碑保留期 180 天**，之后由定时任务物理清理。不能立刻物理删除，否则离线设备重新上线时会把已删除的书签又同步回来。

#### API 契约

统一前缀 `/v1`。除 `/health` 和 `/ready` 外全部要求 `Authorization: Bearer <accessToken>`。

| 端点 | 说明 | 限流 |
| --- | --- | --- |
| `GET /health` | 存活探针 | 无 |
| `GET /ready` | 就绪探针，含一次数据库 ping | 无 |
| `POST /v1/auth/google` | `{ code, codeVerifier }` → Token 对 + 用户信息 | 10 次 / 分钟 / IP |
| `POST /v1/auth/refresh` | `{ refreshToken }` → 新 Token 对，旧 refresh 立即 `consumed_at` | 20 次 / 分钟 / IP |
| `POST /v1/auth/logout` | 吊销当前用户全部未消费 Token | 20 次 / 分钟 |
| `GET /v1/resources?since=&limit=` | 增量拉取，按 `updated_at` 升序，含墓碑 | 60 次 / 分钟 / Token |
| `POST /v1/resources` | 批量上推，单次最多 200 条 | 60 次 / 分钟 / Token |

`GET /v1/resources` 返回：

```
{ "items": [ { "resourceKey", "revision", "payload", "noteVersions", "deletedAt", "updatedAt" } ],
  "nextCursor": "2026-07-30T01:23:45.678Z|a3f2c1..." | null }
```

`since` 省略时为全量首次同步。`limit` 默认 200、上限 500。

**游标必须是 `(updated_at, resource_key)` 复合值，不能只用时间戳，也不能用页码。**

- 用页码：翻页期间有数据变动就会漏条。
- 只用时间戳：一次批量同步会让几百条记录的 `updated_at` 落在同一毫秒。此时 `WHERE updated_at > cursor` 会跳过同毫秒的剩余记录（**静默丢数据**），改成 `>=` 又会无限返回同一页（**死循环**）。

正确的查询条件是字典序比较：

```sql
WHERE user_id = $1
  AND (updated_at, resource_key) > ($2, $3)
ORDER BY updated_at, resource_key
LIMIT $4
```

`since` 为空时省略 `AND` 那一行。`nextCursor` 取本页最后一条的 `updated_at` 和 `resource_key` 拼接，客户端原样回传，不要自己解析或重新构造。

`POST /v1/resources` 请求体：

```
{ "items": [ { "resourceKey", "baseRevision", "payload", "deletedAt" } ] }
```

响应逐条给出结果：

```
{ "results": [ { "resourceKey", "status": "applied" | "merged", "revision", "payload", "noteVersions" } ] }
```

#### 同步协议与冲突解决

客户端记录自己上次拉取到的 `revision` 作为 `baseRevision` 上推。服务端逐条处理：

- **`baseRevision` 等于库内 `revision`** → 干净写入，`revision + 1`，返回 `applied`。
- **`baseRevision` 小于库内 `revision`** → 发生并发修改，服务端做合并，`revision + 1`，返回 `merged` 和合并后的完整载荷，客户端用返回值覆盖本地。

合并规则按字段分三类：

| 字段 | 规则 | 理由 |
| --- | --- | --- |
| AI 生成字段（`summary`、`tags`、`topics`、`aliases`） | 取 `payload.updatedAt` 较新的一方 | 可重新生成，冲突代价低 |
| `note`（用户手写） | **两份都保留，写入 `note_versions` 数组，不覆盖** | 用户自己写的内容丢一个字都不可接受 |
| 封面来源（`coverSource`、`imageUrl`、`categoryCoverId`） | 较新的一方 | 代价为零，本地可重建 |
| `deletedAt` | 删除优先。任一方标记删除即为删除 | 删除是用户明确意图，不该被另一台设备的旧数据复活 |

`note_versions` 非空时，侧边栏的编辑器要显示「这条笔记有 2 个版本」并让用户选择保留哪个或合并，选定后清空 `note_versions`。**不要静默展示其中一个版本**，那等于把冲突处理成了丢数据。

标题、URL、文件夹结构**永远以 `chrome.bookmarks` 为准，云端副本不允许覆盖本地**。这条纪律现有代码已经在执行（`mergeLocalResources` 里 pending 本地态优先），迁移后必须保留。

#### 授权强制：这是最容易出事的地方

失去 Supabase 的 RLS 之后，数据库层不再兜底，漏一个 `user_id` 条件就是全库泄露。要求：

**所有对 `resources` 表的访问必须走唯一的 repository 模块**，该模块的每个导出方法第一个参数都是已验证的 `userId`，且不导出任何不带 `userId` 的查询：

```ts
// server/src/resource-repository.ts —— 唯一允许出现 resources 表 SQL 的文件
export function createResourceRepository(db: Database) {
  return {
    listSince(userId: string, since: Date | null, limit: number): Promise<ResourceRow[]>,
    upsertMany(userId: string, items: ResourceInput[]): Promise<UpsertResult[]>,
    purgeExpiredTombstones(olderThan: Date): Promise<number>
  };
}
```

**写一个会真正失败的结构测试**，而不是靠代码审查：扫描 `server/src/` 下除 `resource-repository.ts` 以外的所有文件，断言不出现 `FROM resources`、`INTO resources`、`UPDATE resources` 这些字符串。这条测试能挡住未来任何一次「顺手在别处写个查询」。

再加一条越权集成测试：建两个用户，用 A 的 access token 请求 `GET /v1/resources`，断言返回结果里不含任何 B 的 `resource_key`。

#### 验收标准

**功能**

- 两台设备登录同一账号，A 设备的 AI 摘要和标签在 B 设备出现。
- B 设备本地无封面缓存时，能仅凭同步来的来源信息重建出与 A 设备一致的封面。
- **B 设备不出现任何来自 A 设备的页面快照**（验证快照不上传）。
- 两台设备同时编辑同一条笔记时，`note_versions` 保留两份，界面提示用户选择。
- 一台设备删除的书签，在另一台设备上也消失（墓碑生效）；离线设备重新上线后不会把它同步回来。
- 断网期间的保存全部进 Outbox，恢复网络后自动补同步，不丢条不重复。
- **翻页游标的同毫秒测试**：构造 500 条 `updated_at` 完全相同的记录，用 `limit=100` 翻完全部页，断言恰好拿到 500 条、无重复、无遗漏、不死循环。这是复合游标唯一有意义的验证方式。

**安全**（每一条都要有对应的自动化测试）

- **伪造的 `id_token` 被拒绝**：构造一个签名无效的 token，断言 401。
- **过期的 `id_token` 被拒绝**。
- **`aud` 不匹配的 `id_token` 被拒绝**（防止用别的应用的 token 登录）。
- 用 A 用户的 access token 请求，返回结果不含任何 B 用户的数据。
- 结构测试通过：`server/src/` 下除 repository 外不存在 `resources` 表的裸 SQL。
- 载荷白名单生效：带 `thumbnailDataUrl` 的请求入库后该键不存在；超过 32KB 的单条 `payload` 被拒绝。
- refresh Token 使用一次后立即失效，重放返回 401。

**运维**

- 单用户 1,000 条书签的云端存储占用不超过 3MB。
- 逻辑备份**实际恢复过一次**，恢复后数据与备份时一致。备份产物落在对象存储，不只在本机。
- 同步压测（模拟 50 用户各 1,000 条全量同步）期间，`console.nexvoice.cc` 的响应时间不出现可观测劣化。
- `aarre-api` 容器 OOM 或崩溃时，NexVoice 的 `control-api` 不受影响。
- 错误上报能在 GlitchTip 里看到，且上报内容不含 Token、书签标题、URL 或笔记正文。

### F15 · 隐私与合规

- 隐私政策页面，明确说明：正文发往哪里、什么数据留在本地、什么数据上云、封面图片请求会访问哪些第三方域名。
- Chrome Web Store 的权限披露文案，逐条解释为什么需要 `history`、`tabs`、`bookmarks`、`unlimitedStorage`。
- 数据导出功能。用户能一键导出全部智能层数据为 JSON。这既是合规要求，也是「我们不锁定你」的最好证明。

### F16 · 计费与配额接口

商业模式尚未确定（见第 9 章），但**代码结构要提前留出接口**，避免将来大改：

- AI 调用统一走一层网关函数，具备用量计数和配额检查的挂载点。
- 用户等级字段预留，即使当前所有人都是 BYOK 层。

不要现在就实现计费，只留接口。

### F17 · 商店素材

正式 Extension ID、图标、截图、宣传视频、商店描述文案。这些是硬门槛，没有就上不了架。

## 8. M4 · 上台阶

### F18 · 周报与月报

**这个功能极容易做成没人看的鸡肋。** 绝大多数产品的周报是「你本周收藏了 23 个链接」，用户看两次就关掉通知。差别在于报告回答的是「我做了什么」还是「我该注意什么」。

五个维度，每一条都要求做到右列而不是中列：

| 维度 | 平庸做法（不要做） | 有价值的做法 |
| --- | --- | --- |
| 注意力迁移 | 本周收藏 23 条，比上周多 5 条 | 「你的关注点从 React 生态转向 AI Agent 架构，这是连续第三周」——用 `topics` 做时间序列对比，这是 Chrome 原生书签永远给不了的洞察 |
| 收而不读 | 通常没有这一项 | 「你有 34 个书签收藏超过 90 天从未打开」——杀伤力最大，因为它戳中了每个人收藏夹的真相 |
| 知识缺口 | 本月热门标签 Top 5 | 「你在 RAG 上收了 12 篇，但全是入门介绍，没有一篇讲评测和上线」——需要 AI 真的读懂内容层次 |
| 重新浮现 | 通常没有这一项 | 「三个月前收藏的这篇，和你这周在看的东西直接相关」——让用户觉得「它真的在帮我」 |
| 健康度 | 总收藏数 1,240 | 「本月新增 47 条中 12 条已失效；3 个文件夹超过 200 条建议拆分」——直接给出可执行提案，一键应用 |

**成本控制的技巧：** 周报不需要每周跑全量 AI。用已经存好的 `summary` / `tags` / `topics` 做本地统计，只在最后生成叙述性总结时调一次 AI。一份周报的成本可以压到一次 API 调用以内，这让免费用户也能用上。

### F19 · 主题图谱

把 `topics` 字段可视化成聚类图，让用户第一次看见自己的知识版图。截图传播性极强，是天然的增长素材。

### F20 · 遗忘曲线重现

按时间衰减把老书签主动推回来，尤其是和当前浏览内容相关的。让产品从「仓库」变成「会说话的助手」。

### F21 · Web / PWA 端

Chrome 移动端跑不了扩展，但原生书签会通过 Chrome Sync 同步到手机。一个只读的 Web 端就能补上移动端缺口。依赖 F14 选择路线一。

| 风险 | 影响 | 应对 |

| Google 在 Chrome 内置书签 AI | 存在性风险 | 防线建在 Google 做不了的三件事上：跨 AI 服务商、BYOK 隐私模式、支持 DeepSeek 等国内可用模型。不要把防线建在「有 AI」上 |

| 页面快照被视为隐私侵犯 | 商店评论和舆情风险 | 只处理新收藏或当前正常打开的已收藏页面；已有图最多每 7 天静默刷新一次。无痕、敏感和内网页面禁 AI/截图，快照永不上传，并在安装权限、引导和隐私政策中明示。见 D9 |
| **自建服务器授权漏洞导致跨用户数据泄露** | 不可挽回的信任事故 | 失去了 Supabase 的 RLS 兜底，授权必须在应用层强制：统一 repository 层，每个方法签名强制传入已验证的 `userId`，不提供无 `userId` 的查询入口。验收里有专门的越权测试。见 F14 |
| 与 NexVoice 共用服务器互相影响 | 一个项目的故障拖垮另一个 | 数据库必须独立（独立 database、独立用户），实例可共用；按用户和 IP 双维度限流；批量上推设条数上限；同步压测时观测 NexVoice 的响应时间 |
| 增强层数据丢失且无法恢复 | 用户最在意的资产没了 | 增强层是用户唯一无法自行恢复的数据（书签有 Chrome Sync，封面可重抓）。机器快照粒度太粗，必须有定时逻辑备份到对象存储，并**实际验证过一次恢复** |

| Chrome 扩展 API 变更 | 功能失效 | `minimum_chrome_version` 已锁 134。关注 MV3 后续变更，特别是 Service Worker 生命周期 |
| 单人维护的持续性 | 用户对长期可用性存疑 | 数据导出（F15）和「不建平行库」本身就是最好的答案：即使产品停止维护，用户的书签一条都不会丢 |

## 11. 明确不做的事

写清楚不做什么，和写清楚做什么同样重要。

- **不做平行书签库。** 任何要求用户「导入书签到 Aarre」的设计都是错的。
- **不做第三方截图服务。** 会把用户 URL 发给第三方，和隐私定位冲突。
- **不做第三方图标服务**（Google S2、DuckDuckGo icons、unavatar）。同上一条的理由，不能因为「只是图标」就放松。
- **不做后台批量开标签页截图。** `captureVisibleTab` 只能截可见标签页，技术上就堵死。
- **不用 AI 生成「看起来像网页」的预览图。** 那是凭空编造，用户会误以为是真实页面。预览窗的可信度不能掺假。
- **不做封面色底合成、不做生成式字标。** 低分辨率图标叠色底不会变精致，只会增加视觉噪音。分类封面已经覆盖这个需求。
- **不上传页面快照到云端。** 快照是设备本地的浏览痕迹，同步它就是把浏览行为搬到服务端。
- **不把任何二进制图像资产上云。** 封面靠来源信息本地重建，服务端有白名单强制剥离。
- **不在服务端做 AI 富化，不在服务端存 API Key。** BYOK 直连是产品的隐私基石，也是成本结构的基石。
- **不复制 Chrome 地址栏的私有能力。** 计算器、单位换算、站点搜索快捷词是未公开实现，承诺了做不到。
- **不做社交与协作。** 共享收藏夹、团队空间是另一个产品，会稀释「个人知识管理」的定位。
- **不在 M1 / M2 阶段做移动端。** 先把桌面单机体验做到无可挑剔。

## 12. 开工指引

这一章是给开发 Agent 的执行说明。第 4 到 8 章是「做什么」，这一章是「按什么顺序做、别碰什么」。

### 12.1 执行顺序与依赖

需求之间有真实依赖，不要跳着做。下面按可以并行的批次组织：

| 批次 | 需求 | 说明 |
| --- | --- | --- |
| **第 1 批**（可三路并行） | F2 撤销栈与回收站 · F1 侧边栏搜索框 · F3 封面策略 | F2 是所有 AI 写操作的前置条件，优先级最高。三者文件重叠少 |
| **第 2 批** | F22 悬浮预览 | 功能上不依赖 F3，但要占用 IndexedDB v4，所以必须等 F3 的 v3 落地 |
| **第 3 批**（可两路并行） | F4 首次引导 · F5 / F6 其余 M1 项 | |
| **第 4 批** | F8 检索改造（只做第一层） | 别名字段要同时改 enrichment prompt，与 F3 的扫描流程有交集，不要和 F3 并行 |
| **第 5 批** | F14 云端迁移 | 依赖 F16 的正式 Extension ID（Google 重定向 URI 需要它）。**开工前先完成 F14 的「四件事确认」** |
| 其余 | 按第 3 章里程碑表 | |

**IndexedDB 版本号是共享资源，必须串行分配**，两个 Agent 同时把版本号改成 v2 会导致其中一方的 store 永远建不出来：

| 版本 | 归属 | store |
| --- | --- | --- |
| v2 | F2 | `undoSnapshots`（撤销快照，按批次） |
| v3 | F3 | `siteBrands`（站点标识，按域名） |
| v4 | F22 | `pageSnapshots`（页面快照，按 canonicalUrl） |

**撤销快照和页面快照是两件完全不同的事，绝对不要都叫 `snapshots`。** 前者是书签树的结构备份，后者是网页截图。同名会让后来读代码的人做出灾难性的误判。

### 12.2 文件归属

领取需求后独占下列文件，并在 `AGENT_PROGRESS.md` 登记：

| 需求 | 主要文件 |
| --- | --- |
| F1 搜索框 | `src/lib/search.ts`、`SidePanelApp.tsx`（需登记） |
| F2 撤销栈 | `src/lib/storage.ts`、`src/extension/background.ts`（需登记） |
| F3 封面 | 新建 `src/lib/cover-registry.ts`、改 `src/lib/thumbnail.ts` / `page-essence.ts` / `favicon.ts`、`src/ui/components/SiteThumbnail.tsx` |
| F8 检索 | `src/lib/search.ts`、`src/lib/local-ai.ts`（enrichment prompt 加 `aliases`） |
| F22 悬浮预览 | 新建 `src/ui/components/BookmarkPreview.tsx`、`src/lib/snapshot.ts`；改 `SidePanelApp.tsx`（需登记） |
| F14 云端 | `src/lib/auth.ts` / `cloud.ts` / `supabase.ts`、`scripts/build.mjs`、新建 `server/` |

`src/lib/storage.ts` 的 `normalizeResourceRecord` 会被多个需求同时想改（都要加新字段）。**加字段时只做追加，不要重排、不要改已有字段的默认值**，这样多个 Agent 的改动可以自然合并。

### 12.3 每次改动都要遵守的既有纪律

这些是现有代码已经在执行的原则，改动时不要破坏：

1. **原生层是唯一事实来源。** 标题、URL、文件夹结构永远以 `chrome.bookmarks` 为准，本地和云端副本都不允许覆盖它。
2. **`normalizeResourceRecord` 必须向后兼容。** 任何新字段都是可选的，旧记录读出来不能报错。
3. **IndexedDB 升级函数必须保留现有 `resources` 和 `outbox` 数据。** 不允许用「删库重建」的方式升级。
4. **AI 写操作前必须有快照。** 快照写入失败就拒绝执行操作，不允许「先做了再说」。
5. **通配网页权限只服务完整增强层。** `<all_urls>` 是原生星标自动增强与 `captureVisibleTab()` 所必需的 `host_permissions`；业务逻辑只处理 HTTP(S) 收藏，不得用它读取无痕/敏感/内网页面、调用 AI 或上传快照。普通浏览只做本地 URL 命中检查，未收藏网页不读取正文；命中已收藏页面才补缺图或按 7 天新鲜度静默刷新。新增其他权限仍须单独说明理由。
6. **不引入需要额外权限的能力**而不在 PRD 里说明。新增任何 manifest 权限都要在进展文档里写明理由，因为它会影响商店审核。

### 12.4 不要做的事

- **不要为了让测试通过而放宽验收标准。** 第 5 章的「零上采样」和「兜底率 ≤ 12%」是互相拉扯的硬指标，达不到就报出来，不要单独满足一个。
- **不要用模拟数据代替真实验证。** 完成定义里的「在真实 Chrome 中加载 `dist/`」不能用 `?preview=1` 替代。
- **不要顺手重构不属于本需求的代码。** 两个高冲突文件尤其如此。
- **不要自行决定 D 系列的待决策项。** 第 9 章里还没标「已定」的（D1、D3、D5、D6、D7、D11）需要产品负责人拍板，遇到就停下来问。
- **不要在服务端记录任何书签内容。** 日志里不能出现标题、URL、笔记、Token、API Key。

### 12.5 每完成一个需求要做的事

1. 跑 `npm run check`，确认全绿并记下测试数量。
2. 在真实 Chrome 里加载 `dist/` 人工走一遍验收标准的每一条。
3. 在 `AGENT_PROGRESS.md` 顶部追加一节，写清楚：改了什么、怎么验证的、哪些验收项没达成及原因、有没有留下待办。
4. 从进展文档的文件独占登记里移除自己。
5. **验收标准里有任何一条没达成，必须在进展文档里显式写出来**，不要默认「大概没问题」。
