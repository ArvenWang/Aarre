## 0. 这份文档怎么用

这是一份**可直接执行**的整改清单，交给 Agent 按顺序做。每一条都写清了：现状是什么、为什么要改、改成什么样、怎么验收、动哪些文件。

三条硬性要求：

1. **按批次顺序执行，不要跳批。** 批次内的条目可以并行，跨批次有依赖。
2. **每完成一批，更新 `AGENT_PROGRESS.md`，并单独提交一次。** 不要把六批攒成一个提交。
3. **每一条的「验收标准」都要真的跑一遍再打勾。** 如果某条只能在真实 Chrome 安装态下验证，写明「待真机验收」，不要写成已完成。上一轮交付在这一点上是诚实的，请保持。

**开工前必读：`docs/PRD.md` 的 F22 已于 2026-07-30 修订。** 悬浮预览现在的正确形态是「只有一张页面快照，没有信息区、没有站点标识、没有采集时间角标，没有快照时整个悬浮层不渲染」。**不要恢复信息区**——当前代码在这一点上是对的，PRD 是刚刚被改成和代码一致的，不是反过来。

## 1. 上一轮交付的总体判断

地基做得比预期好，缺口集中在两处：**最后一公里的产品触达**，和 **PRD 点名的硬指标没有被验证**。

做得好、**不要在整改中破坏**的部分：

- **撤销安全做到了偏执的程度。** `runProtectedBookmarkMutation` 是写前快照、快照失败拒绝执行、二次状态回写失败时自动把书签回滚。所有 `chrome.bookmarks` 写方法的调用点都有保护。整改涉及删除逻辑时必须继续走这条通道。
- **IndexedDB v1→v4 按 `oldVersion` 增量建表**，老用户跳版本升级不会丢数据，两种快照（`undoSnapshots` / `pageSnapshots`）命名没有混淆。
- **权限克制。** `host_permissions` 只有三个 AI 服务商域名，`http://*/*` 在 `optional_host_permissions`。快照采集用 `tab.incognito` 判断无痕。数据导出有测试断言不含 API Key。
- **悬浮预览没有拿 `og:image` 或分类封面充数。** 这条纪律在整改后也必须守住。

需要知道的一个背景事实：**`SidePanelApp.tsx`（4,620 行）和 `background.ts`（3,300 行）目前的自动化测试用例数是 0。** 98 项测试全部落在 `src/lib/` 的纯函数上。所以「`npm run check` 全绿」在当前覆盖结构下只能保证不崩，保证不了行为符合预期——第 6 批就是来补这个的。

## 第 1 批 · 兑现已有能力

这一批的共同特征是：**能力已经在代码里了，但被一行文案、一个参数或一处方向写反给抵消掉了。** 改动量都很小。

### 1.1 删除确认文案说了反话（F2）

**现状**

`src/ui/sidepanel/SidePanelApp.tsx` 4443–4447 行：

```
将从 Chrome 永久删除这个书签，此操作无法撤销。
将永久删除整个文件夹及其中 N 个书签，此操作无法撤销。
```

**为什么要改**

后台为删除做了很重的功课——写前快照、递归序列化整棵子树、30 天内可在设置页「最近的更改」里恢复。这句文案把这些全否掉了。后果是双向的：谨慎的用户不敢用删除，果断的用户删完不知道还能恢复。

F2 在 PRD 里的定位是「在补上撤销之前，让 AI 整理书签这件事在道义上就不该向用户推广」。这句文案等于把这个前置条件的价值抹掉了。

**怎么改**

改成如实描述，并指出恢复路径：

- 单个书签：`将从 Chrome 删除这个书签。30 天内可以在设置页「最近的更改」里恢复。`
- 文件夹：`将删除整个文件夹及其中 N 个书签。30 天内可以在设置页「最近的更改」里恢复。`

同时在设置页「最近的更改」区域的标题下加一句说明，告诉用户这里能恢复什么、保留多久。

**验收标准**

- 删除确认框不再出现「无法撤销」「永久删除」字样。
- 删除一个含 5 条书签的文件夹后，能在设置页「最近的更改」里完整恢复出文件夹结构和全部 5 条书签。
- 恢复后书签的所在位置、排序与删除前一致。

**涉及文件**：`src/ui/sidepanel/SidePanelApp.tsx`

### 1.2 悬浮预览的意图检测方向写反（F22）

**现状**

`src/ui/sidepanel/SidePanelApp.tsx` 1758–1763 行：

```tsx
if (distance / elapsed > 0.65) {
  armPreview(node, event.currentTarget);   // 速度超阈值，却启动了 400ms 计时器
  onPreviewLeave();                         // 紧接着又关闭预览
} else if (previewTimer.current === undefined) {
  armPreview(node, event.currentTarget);
}
```

**为什么要改**

PRD 要求的是「鼠标移动速度**高于**阈值时**不计时**」。当前实现在高速分支里反而调用了 `armPreview`（它会清掉旧计时器并重新起一个 400ms 计时器），紧接着又调 `onPreviewLeave` 关闭已显示的预览——两个动作互相矛盾。

实际影响有限（离开该行时 `onPointerLeave` 会 `cancelPreview`），但「快速甩动后停在某一行」会立刻触发预览，而且这段代码的意图完全读不出来，下一个人改到这里必然会踩坑。

**怎么改**

高速分支应该**取消**计时并隐藏预览，低速分支才启动计时：

```tsx
if (distance / elapsed > 0.65) {
  cancelPreview();
} else if (previewTimer.current === undefined) {
  armPreview(node, event.currentTarget);
}
```

注意 `cancelPreview` 会把 `pointerSample.current` 置空，下一次 `onPointerMove` 会因为 `!previous` 直接 return，相当于重新采样一次才开始判断——这个行为是想要的，不用额外处理。

顺带修一处无障碍问题：`BookmarkPreviewCard`（1891 行）现在只有一张图，对屏幕阅读器没有任何信息价值，但仍带着 `aria-label={节点标题的预览}`。改成 `aria-hidden="true"` 并去掉 `aria-label`，避免朗读一个空容器。键盘按 `P` 唤出的路径保留——它服务的是低视力但用眼的用户。

**验收标准**

- 以明显高于日常的速度连续划过 20 行书签，全程不出现悬浮层。
- **反向用例：** 缓慢移到某一行上停住，400ms 后悬浮层正常出现。这条必须一起验，用来捕捉方向再次写反。
- 快速甩动后停在某一行上，需要重新停留满 400ms 才出现，不是立刻出现。
- 屏幕阅读器遍历书签列表时不会朗读到预览容器。

**涉及文件**：`src/ui/sidepanel/SidePanelApp.tsx`

### 1.4 搜索命中项没有高亮（F1）

**现状**

F1 的「怎么做」第一条就是「实时过滤当前书签树，命中项高亮」。过滤和自动展开都做了，高亮没做——`BookmarkTree` 组件根本没有接收查询词。

**怎么改**

把当前查询词透传给 `BookmarkTree`，在书签标题渲染时把命中片段包一层 `<mark>`。

三点注意：

- **匹配范围要和搜索逻辑一致。** `src/lib/search.ts` 的匹配包含子串、中文二元组和拼音三种，高亮不必覆盖拼音（拼音命中时原文里没有对应字符可标），但**子串命中必须标**，否则用户会疑惑「为什么这条会出现在结果里」。
- 高亮样式用现有的强调色，不要引入新颜色。深色模式下要保证对比度。
- 标题里可能含用户数据，用 React 元素拼接，**不要用 `dangerouslySetInnerHTML`**。

**验收标准**

- 搜索一个词，结果列表中所有标题里出现该词的位置都被高亮。
- 搜索一个只能靠拼音命中的词（如用 `bilibili` 搜中文标题），结果正常出现、不高亮、不报错。
- 标题包含 `<`、`&`、emoji 时高亮不破坏渲染。
- 清空搜索框后高亮全部消失。

**涉及文件**：`src/ui/sidepanel/SidePanelApp.tsx`（`BookmarkTree` 及其调用点）、`src/ui/styles.css`

## 第 2 批 · 让 F7 能被用户看见

PRD 对 F7 的原话是「这是整个产品最重要的一个功能」。**这一批是本轮投入产出比最高的部分：逻辑全都写完了，质量也不差，缺的只是入口。**

### 2.1 现状

- 四类发现的判定逻辑、勾选、批量应用、整批撤销全部写完，边界规则也守得住（删除类默认不勾、失效判定严格基于 HTTP 检测结果、生成过程 0 次 AI 调用）。
- 但 `buildLibraryInsights` 只在用户主动打开全页管理器时才被调用（`src/extension/background.ts` 2829–2839 行的 `getLibraryInsights`，仅由消息触发）。**扫描结束后没有任何回调、通知、角标或提示。**
- 而进入全页管理器的唯一入口，是侧边栏右上角一个**没有文字的图标按钮**（只有 `title` 属性）。进去之后还要自己找到「整理提案」这个 tab。

PRD 要求的是「扫描完成后自动生成提案」并在提案产生时「主动引导」用户去全页处理。现在这条链路的入口是关着的。

### 2.2 怎么改

**（a）扫描完成后自动生成提案**

在库扫描任务完成的收尾处调用 `buildLibraryInsights`，把结果连同生成时间写进 `chrome.storage.local`。要求：

- 生成过程**不得触发任何 AI 调用**——现有实现本来就是纯本地计算，保持这一点，不要为了「更聪明」加 AI。
- 结果要带上生成时的资源指纹（书签总数 + 最后更新时间），用户打开全页时如果指纹已变，重新计算而不是展示陈旧提案。
- 生成失败不能影响扫描本身的完成状态。

**（b）扩展图标角标**

有新提案时在扩展图标上打角标（复用现有的 `flashActionBadge` 相关能力，但这个是常驻的，不是一闪而过）。角标显示提案条数，上限显示 `99+`。用户处理完或主动忽略后清除。

**（c）侧边栏的带文字入口**

在侧边栏书签列表上方加一条可关闭的提示条，形如：

```
发现 12 条可以整理的地方 · 3 个重复、5 条失效、4 条可归类     [去处理] [暂不]
```

要求：

- 有提案时才出现，没有时不占位。
- 「暂不」关闭后 24 小时内不再出现，除非提案内容发生变化。
- 「去处理」直接打开全页管理器**并定位到「整理提案」tab**，不要只是打开全页让用户自己找。
- 右上角那个无文字图标按钮保留，但加上可见文字标签或至少加 `aria-label`。

**（d）全页各视图都能回侧边栏（F5）**

全页管理器的 6 个视图里目前只有「书签库」那个有回侧边栏的入口。把返回入口提到全局导航层，让 6 个视图都能回。这一条和 F7 的触达是同一个问题的两面，一起做。

### 2.3 验收标准

- 完成一次库扫描后，**不打开全页管理器**的前提下：扩展图标出现角标，侧边栏出现提示条，两者数字一致。
- 提示条文案里的分类数量与全页「整理提案」tab 里的实际条目数一致。
- 点「去处理」直接落在「整理提案」tab 上。
- 点「暂不」后关闭侧边栏再打开，提示条不再出现；手动新增 3 条重复书签并重新扫描后，提示条重新出现。
- 提案全部处理完毕后角标清除。
- 扫描过程中人为让 `buildLibraryInsights` 抛错，扫描仍然正常标记为完成。
- 生成提案的整个过程中 AI 调用次数为 0（在 Network 面板确认无服务商请求）。
- 全页管理器的 6 个视图都能一键回到侧边栏。

**涉及文件**：`src/extension/background.ts`、`src/ui/sidepanel/SidePanelApp.tsx`、`src/ui/manager/ManagerApp.tsx`、`src/ui/styles.css`

## 第 3 批 · 逻辑正确性

### 3.1 Chrome 原生书签管理器里的删除不进回收站（F2）

**现状**：`src/extension/background.ts` 3271–3288 行的 `chrome.bookmarks.onRemoved` 监听器只是把该 ID 从 `nativeBookmarkIds` 里摘掉，没有写撤销快照。

**为什么要改**：F2 写的是「用户手动删除的书签也进快照 store」。从 Aarre 侧边栏删除有完整保护，但用户在 Chrome 自己的书签管理器里删除时什么都不留。用户不会区分「我是从哪里删的」。

**怎么改**：在 `onRemoved` 里，摘除绑定之前先写一条撤销快照，快照内容与 Aarre 内部删除保持同一格式，来源标记为「Chrome 书签管理器」以便在「最近的更改」里区分。

两个坑：

- **`onRemoved` 对文件夹只触发一次**（携带整棵子树的 `removeInfo.node`），不会为子节点逐个触发。要从 `removeInfo` 里递归取子树，不能只处理顶层。
- Aarre 自己发起的删除也会触发 `onRemoved`。已有 `internalBookmarkIds` 机制用于识别内部操作，**必须复用它做去重**，否则同一次删除会写两条快照。

**验收标准**

- 在 Chrome 原生书签管理器里删除一条书签，Aarre 设置页「最近的更改」里出现该条记录并可恢复。
- 在原生管理器里删除一个含 5 条书签的文件夹，恢复后结构和 5 条书签全部回来。
- 从 Aarre 侧边栏删除一条书签，「最近的更改」里**只有一条**记录，不是两条。
- 30 天过期清理对两种来源的快照一视同仁。

### 3.2 从 Aarre 打开书签后要等 5 秒才采集快照（F22）

**现状**：`schedulePageSnapshotForTab` 默认 `delay = 5_000`（`background.ts` 1252–1265 行）。收藏当前页的路径传了 `0`（1489 行），但「从 Aarre 点开一个书签」走的是通用的 `chrome.tabs.onUpdated` 路径（3205–3209 行），吃的是 5 秒延迟。

**为什么要改**：F22 把「用户从 Aarre 点开一个书签」单列为一个采集时机，理由是「这一条直接覆盖存量书签」。而按修订后的 F22，**没有快照就完全没有悬浮预览**——快照库的覆盖速度直接决定这个功能什么时候开始存在。5 秒延迟意味着用户点开后秒关的页面永远补不上快照。

**怎么改**：在 Aarre 打开书签时记下 tabId 和目标 URL，页面 `status === "complete"` 且 URL 匹配时立即采集（`delay = 0`），不走 5 秒路径。普通浏览命中书签的场景保持 5 秒不变。

注意采集前仍要走现有的全部前置检查：仅 `http/https`、非无痕、不在排除域名清单里、该标签确实是当前窗口的活动标签。

**验收标准**

- 从 Aarre 点开一条没有快照的书签，页面加载完成后 1 秒内产生快照；回到侧边栏 hover 该条，悬浮层出现。
- 页面加载完成后立刻关闭标签页，快照仍然已经落库。
- 从 Aarre 打开一个排除清单内的域名，不产生快照。
- 无痕窗口里打开，不产生快照。
- 普通浏览到一个已收藏 URL 时仍然是停留 5 秒后采集，不是立即采集。

### 3.3 同域名限速从任务开始计时，不是结束（F11）

**现状**：`src/lib/scan-scheduler.ts` 68–74 行，`lastStartedAt` 在任务**开始前**写入。如果单次请求耗时超过 1 秒，下一次请求的等待时间算出来是负数，立即开始，实际间隔为 0。

**为什么要改**：F11 要求「同域名串行且间隔不低于 1 秒」，目的是不被目标站点限流。慢站点恰恰是最容易触发限流的那批，而当前实现对慢站点完全不限速——正好反了。

**怎么改**：把时间戳的写入移到任务结束后（`finally` 里），语义从 `lastStartedAt` 改为 `lastFinishedAt`。任务抛错时也要记录，否则连续失败会变成不限速的重试风暴。

**验收标准**

- 新增单元测试：同域名两个任务，第一个耗时 3 秒，断言第二个的开始时间距第一个的**结束**时间不少于 1 秒。
- 新增单元测试：第一个任务抛错，第二个仍然被限速。
- 现有的「跨域名并行不互相阻塞」测试仍然通过。

**涉及文件**：`src/lib/scan-scheduler.ts`、`tests/scan-scheduler.test.ts`

### 3.4 F7 和 F12 各写了一套「可归类」判定

**现状**：`src/lib/library-insights.ts` 里 `buildLibraryInsights`（303 行起，F7 的可归类提案）和 `suggestFolders`（338 行起，F12 保存时的文件夹建议）用了两套不同的算法判断「这条书签应该归到哪」。

**验收标准**

## 第 4 批 · F3 封面兜底率

**这一批必须按 4.1 → 4.2 → 4.3 的顺序做，不要跳过 4.1 直接堆规则。**

PRD 5.9 定了两条互相拉扯的硬指标：「零上采样」和「分类封面兜底率 ≤ 12%」。前者代码层面已经做到（缩放比硬限制 ≤ 1）。后者的现状是：**既没有实现支撑，也没有任何测量手段**——不知道现在是多少，也就无从判断改动有没有效果。

### 4.1 先做兜底率测量工具（前置，必做）

**为什么先做这个**：现在补规则表是在猜。补 100 条规则可能把兜底率从 40% 降到 15%，也可能只降到 35%——因为真正卡住的可能是别的环节（见 4.2）。没有测量，后面两步都是盲改。

**怎么做**

写一个开发期脚本（放 `scripts/`，不打包进 `dist/`），输入一份书签 URL 清单，跑完整的封面管线，输出：

- 总数、各来源命中数与占比（规则表 / `apple-touch-icon` / manifest icons / 高分辨率 `rel=icon` / `og:image` / 分类封面兜底）
- 兜底率
- 被质量闸门拒掉的资产清单，按拒绝原因分组（`below-128px` / `non-square` / `low-ink-or-contrast`），每组带样例 URL
- 按域名聚合的兜底 Top 30——这份清单直接就是 4.3 补规则表的输入

样本用真实书签库导出，不少于 300 条，覆盖中英文站点。样本文件不要提交进仓库（可能含隐私），提交脚本和一份脱敏的结果报告即可。

**验收标准**：能跑出上述报告，并把首次测得的兜底率数字写进 `AGENT_PROGRESS.md`。

### 4.2 补上透明背景合成

**现状**：`src/lib/thumbnail.ts` 183 行只有 `context.clearRect(...)`，没有 `fillRect`。画布保持透明。

**为什么要改**：PRD 5.5 专门为了提高命中率放宽了这一条——「否则会挡掉大量 SVG 和 `rel=icon` 资产，与压低兜底率的目标直接冲突」。当前没做，等于又把这批资产挡在门外。

附带一个更隐蔽的问题：墨迹闸门 `inspectPixels` 的对比度是拿白底算的，深色模式下判断不准。

**怎么改**

- 在 `drawImage` 之前 `fillRect` 一层卡片表面色作为底。
- 底色不要写死白色。**需要为浅色和深色两套主题各生成一份并都存下来**，显示时按当前主题取——运行时再合成会在每次渲染时产生开销，而且 Service Worker 里拿不到主题。存储成本是可接受的：站点标识按域名共享，1,000 条书签大约 200 个域名，翻倍后约 4MB。
- 墨迹闸门的对比度计算改成基于实际使用的底色。

**验收标准**

- 用 4.1 的脚本在同一份样本上重新测量，`low-ink-or-contrast` 的拒绝数量明显下降，并把前后数字记进 `AGENT_PROGRESS.md`。
- 补单元测试：一张纯透明背景 + 深色图形的 PNG，合成到浅色底后通过墨迹闸门；同一张图合成到深色底后也通过。
- 深色模式下抽查 20 个站点标识，没有出现「深色图形贴在深色底上看不见」的情况。
- 现有的 SVG 安全测试仍然通过。

## 第 5 批 · 性能

### 5.1 拼音库 297KB 被预加载进侧边栏首屏

**现状**：`src/lib/search.ts` 第 1 行直接 `import { pinyin } from "pinyin-pro"`，字典表被打进侧边栏首屏必加载的共享 chunk `usage-stats-*.js`（实测 297,604 字节未压缩），并且写进了 `dist/sidepanel.html` 的 `modulepreload`。

**为什么要改**：扩展从本地磁盘读取，不走网络，**gzip 完全不起作用**——每次打开侧边栏都要实打实解析这 297KB。F1 的验收标准是 1,000 条书签下首帧 100ms 以内，这个包是最大的单项开销。而拼音只在用户真正输入拼音时才需要。

**怎么改**

改成动态 `import()`，在用户首次输入疑似拼音（纯 ASCII 字母且长度 ≥ 2）时才加载。加载期间先用子串和二元组给出结果，拼音结果到达后再合并——**不要因为等拼音库而阻塞已经能算出来的结果**。

同时确认 `usage-stats` 这个 chunk 里还有什么：它的名字和拼音库毫无关系，说明 Vite 的自动分包把不相关的模块合到了一起，值得顺便看一眼分包配置。

**验收标准**

- `dist/sidepanel.html` 的 `modulepreload` 列表里不再包含含拼音字典的 chunk。
- 侧边栏首屏加载的 JS 总量比改动前减少 250KB 以上（记录前后数字）。
- 输入拼音仍能正常召回中文书签，首次输入时最多一次短暂延迟，第二次起无延迟。
- 拼音库加载失败时搜索降级为子串 + 二元组，不报错、不白屏。

### 5.2 搜索没有防抖

**现状**：`SidePanelApp.tsx` 2882–2929 行的几个 `useMemo`。索引本身缓存得没问题（只在 `resources` 变化时重建），但每一次按键都会同步跑一遍 O(n) 索引扫描加一遍整棵书签树的递归过滤，两条路径都没有防抖。

**怎么改**：加 120–150ms 防抖。注意**输入框本身必须保持无延迟受控**，只对「计算结果」防抖，不要让用户感到打字卡顿。清空搜索框应当立即生效，不走防抖。

**验收标准**

- 2,000 条书签的库里连续快速输入 10 个字符，输入框显示无延迟，结果列表在停止输入后 150ms 内更新。
- 清空搜索框立即恢复完整书签树。
- F1 原有的「Esc 恢复」行为不受影响。
